## Что решаешь ты

**Спор 17 — срок хранения закрытых ответов.** После контракта выдачи (набор метрик фиксируется при первом release) хранение raw **не даёт** новых опубликованных разрезов по выпущенному раунду — ни в A, ни в B. Оно даёт только: пересчёт тех же метрик после исправления ошибки и офлайн-анализ без публикации (в 21A — только оператор, в 21B — raw-экспорт под AuditLog); перепроверка правил FUNN считается по снимкам и raw не требует. A (Astra): окно 90 дней после закрытия раунда. B (Fable): окно 12 месяцев — правила, исправленные после первой кампании, можно пересчитать по ней; год псевдонимных данных; срок в уведомлении. Стоимость реализации одинакова. **Правило:** «снимки заранее выбранных показателей, пересчёт в пределах 90 дней» → A; «пересчёт тех же метрик или офлайн-анализ в течение года после первой кампании» → B. Зависят задачи 0.18, 0.19, 1.31, 1.36.

**Спор 21 — кто не должен восстановить отдельный ответ сотрудника.** A (Astra): админ-UI не доверен никому; единственный доверенный — оператор базы out-of-band под журналом (предусловие: SSH/root и env с credentials у одного человека); только released-снимки с подавлением по истории выдач, без raw-экспорта; цена M, меньше обратной связи в кампании. B (Fable): трое админов доверены под AuditLog; живые агрегаты с порогом; raw-экспорт только с причиной и записью; цена S, остаточный риск — differencing живого вида самими админами. **Правило:** «руководитель клиента и внешние» → B; «и трое админов» → A; «и оператор базы» → ни A, ни B, нужна отдельная архитектура — отдельное решение. Зависят задачи 0.15, 0.15b, 0.18, 1.20, 1.26, 1.27, 1.30, 1.32.

**Часть руководителя — подтверди (обещание респондентам, одинаково в A и B).** Рекомендовано (a): ответы руководителя вне порога k — отдельный эндпоинт по одному клиенту, только админ-сессия, каждое чтение в AuditLog, не попадают в снимки/CSV/ассистента/Atlas/автоотчёт; пометка «ikkje anonymt» в форме и в уведомлении (как сейчас: «desse svara er ikkje anonyme på same måte»). Альтернатива (b): под порог k — раздел пуст у всех шести клиентов, паритет по руководителям теряется.

**Открытые вопросы:** 3) целевые RPO/RTO и кто восстанавливает без тебя — ворота G3; 4) носитель для проверки букмола в этапе 1; 5) OpenAPI Atlas и админ тенанта Entra; 6) язык `docs/` в репо — оставлен русский.

**Устаревшая строка:** `astra/HANDOFF.md` строка 31 — «Opus 5.5 high»; политика от 11.10 назначает Opus 5.5 `medium` на код, PRINCIPLES §20 уже по ней. Нужно твоё подтверждение и правка HANDOFF.

## Что исправлено после проверки одобрения

- N1 (Astra): ADR-017 согласован с фиксацией метрик — честно описано, что даёт и чего не даёт хранение raw; правило выбора 17 переформулировано; новые ретроспективные публикации — только через отдельный безопасный механизм вне scope.
- Руководители (ревьюер): правило для `part = leader` в ADR-021 «Принято», отражено в PRINCIPLES §6, ARCHITECTURE §5, задачах 0.18, 1.14, 1.27, 1.32.
- Non-blocking: старые коды kartlegging (~59 бит) не импортируются как действующие — только hash для «avslutta» (ADR-009, 1.7, 1.34, 1.35); предусловие варианта A о единственном держателе SSH/env и login event trigger вместо pgaudit на общем инстансе (ADR-021, 0.5, 0.8); корзина SharePoint 93 дня — проверка purge или честный максимум +128 дней (ADR-016, ADR-017, 0.10, 0.19); устаревшие формулировки в ARCHITECTURE и ADR-019 убраны.
- Второй проход (Astra Reject по двум текстовым противоречиям, Fable-ревьюер Approve): PRINCIPLES §6 называет оба исключения (руководители; raw-экспорт common в 21B), ARCHITECTURE §5 ограничивает исключительность raw-экспорта общей частью и обуславливает «35 дней» подтверждённым purge (иначе до 128); 0.5 и 0.8 помечены [21] и входят в G2; G2 включает подтверждение правила для руководителей; ADR-017 оставляет только два реальных плюса хранения raw; ADR-020 вводит population `leaders_all` для сводки «X av Y leiarar».
- Ранее (раунд 3): B5 — приёмка 0.10 только при RPO/RTO ≤ целей, иначе 0.10b; B7 — `privacy.release()` с подавлением по истории выдач и отрицательными тестами; B9 — архив `svar.jsonl` при cutover, удаление по наиболее раннему из трёх сроков.
