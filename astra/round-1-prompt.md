# Архитектура платформы Varde

Oct 11, 2026 · @Oleksandr

Предлагаю вырастить из kartlegging одну платформу, где опросы и семинары — два шага одного цикла работы с клиентами, а AI-ассистент готовит черновики и никогда не публикует сам. Рабочее название Varde: каменная пирамидка, которая показывает путь. Это первый раунд brainstorm: каждое решение ниже сформулировано так, чтобы GPT-6 Astra мог согласиться, возразить или дополнить по пунктам.

## Куда это растёт

Сегодня kartlegging — один опрос с дашбордом. Цель — постоянный разговор с клиентской базой, где каждый шаг даёт материал для следующего: опрос показывает, где клиенты слабы, семинар закрывает самую частую слабость, следующий опрос проверяет, помогло ли.

*(Диаграмма «Цикл работы с клиентом»: четыре шага по кругу — Опрос → Выводы → Семинар → Опрос после; в центре ассистент, от него пунктирные стрелки к шагам «Опрос» (черновик вопросов) и «Семинар» (пакет семинара). Пунктир = ничего не уходит клиенту без человека.)*

Ассистент стоит в центре и кормит два шага черновиками: вопросы для опроса и пакет для семинара. Пунктир означает, что без человека ничего не уходит клиенту. Через год такой работы у каждого клиента есть история: какие раунды прошёл, на каких семинарах был, что изменилось в цифрах. Это и есть то, что Vardahei продаёт как советник, а не как подрядчик.

## Что берём из kartlegging, что меняем

Текущий kartlegging остаётся в работе до конца первой кампании. Платформа строится рядом и впитывает его данные, а не ломает его по ходу.

| Что | Сейчас | В платформе |
| --- | --- | --- |
| Вопросы, советы, сценарии | Код в `sporsmal.js`, логика показа вопросов и советов — JS-функции | Шаблоны опросов в базе, с версиями. Логика — декларативные выражения (JsonLogic), чтобы их мог писать ассистент, править редактор и проверять сервер |
| Выводы для дашборда (FUNN) | Правила зашиты в `dashboard.html` | Правила — записи в базе: условие, порог, текст, предлагаемое действие. Один движок считает их по клиенту, по раунду и по всей базе клиентов |
| Ответы | `svar.jsonl`, один файл | Postgres. Каждый ответ ссылается на точную версию шаблона и на раунд. Текущие ответы и Forms-раунд импортируются как раунды 0 и 1 |
| Сравнение между раундами | Три вопроса сопоставлены вручную | «Якорный ключ» у вопроса, независимый от версии шаблона. Тренд по каждому якорю и клиенту строится сам |
| Страница опроса с туристом и советами | Один HTML | Остаётся почти как есть: отдельный лёгкий «раннер», который получает шаблон с сервера. Тот же раннер работает как голосование на семинаре |
| Админ-панель и дашборд | Две страницы на чистом JS | Одно приложение на React: клиенты, кампании, редактор шаблонов, семинары, ассистент |
| Вход | Логин и пароль, три аккаунта | Вход через Microsoft Entra (рабочая учётка Vardahei, MFA уже есть). Один локальный админ на случай сбоя Entra |
| Ссылки с кодом клиента, анонимность, порог 3 человека на роль | Есть | Остаётся как принцип платформы, записан в `PRINCIPLES.md`, проверяется тестами |

Стиль вопросов, который мы выработали (без жаргона, поведение вместо знаний, сценарии, «veit ikkje» как нормальный ответ, никаких продуктов в тексте), становится инструкцией для ассистента и контрольным списком для ревью.

## Как устроена система

Один контейнер с тремя частями внутри, своя база в уже работающем Postgres, и три внешних сервиса Microsoft, которые у Vardahei и так есть.

*(Диаграмма «Компоненты и связи»: сверху Респонденты (телефон, ссылка с кодом клиента) и Команда Vardahei (трое); справа внешние сервисы — Entra ID (вход команды), Azure OpenAI EU (модель), Microsoft Graph (убран из этапов). Внутри VPS Vardahei: Caddy (atlas-edge) → контейнер Varde = Runner (Preact/vanilla, для респондентов) + Admin (React) + API (NestJS, pg-boss, адаптер модели, модуль assistant) → Postgres 17 (своя база, рядом с базой Atlas). Atlas — отдельный сервис на той же машине: отдаёт список клиентов, принимает агрегированные выводы как observations. Синим — новое, без заливки — то, что уже работает.)*

С Atlas две связи, обе через API: Varde берёт оттуда список клиентов и отдаёт назад агрегированные выводы по клиенту, чтобы советующий слой Atlas видел их рядом с данными Atera и Huntress. Общей базы нет: анонимные ответы не должны лежать в одной схеме с графом «клиент → человек → устройство», иначе один неаккуратный JOIN отменит анонимность, которую мы обещали людям.

## Модель данных

Центр модели — «раунд»: конкретная версия шаблона, запущенная для набора клиентов в определённое время. Всё сравнение и все выводы считаются относительно раунда.

| Сущность | Что хранит | Зачем |
| --- | --- | --- |
| Client | slug, название, отрасль, число сотрудников, язык по умолчанию, ссылка на запись в Atlas | Зеркало списка клиентов из Atlas, база для процента отклика |
| Contact | имя, почта, роль у клиента, согласие на приглашения | Кому отправлять ссылки и приглашения на семинары. Единственные персональные данные в системе |
| SurveyTemplate, TemplateVersion | шаблон и его неизменяемые версии: вопросы, переводы, логика, советы, сценарии с правильными ответами | Черновик правится, опубликованная версия нет. Ответ всегда знает, на какой текст вопроса он дан |
| Question (внутри версии) | id, тип, тексты, варианты, условие показа, `anchor_key` | Якорный ключ связывает один и тот же вопрос через версии и раунды |
| Round | версия шаблона, набор клиентов, окно дат, код доступа на клиента, статус, тип (обычный, после семинара, живой опрос на семинаре, внешний импорт) | То, что сейчас размазано по `tilgang.json` и `kundar.json` |
| Response | раунд, клиент, роль, язык, ответы (JSONB), длительность. Без имён и IP | Анонимный ответ одного человека |
| ProgressEvent | раунд, клиент, анонимный id сессии, номер вопроса, время | Панель «кто отвечает сейчас» и «где бросают». Удаляется через 90 дней |
| FindingRule | условие (JsonLogic над якорными ключами), пороги, текст, серьёзность, ссылка на Action | Выводы дашборда как данные, а не код. Работают на любом раунде с теми же якорями |
| Finding | раунд, клиент (или все), правило, числа, статус (новый, в работе, закрыт) | Вычисленный вывод, который можно взять в работу и отдать в Atlas |
| Action | название услуги или меры («Bitwarden-пилот», «план реагирования на одну страницу»), описание, тема семинара, которая её закрывает | Каталог того, что Vardahei предлагает в ответ на вывод. Связь опросов с семинарами и услугами |
| Seminar | тема, дата, формат, целевые клиенты, программа, материалы, ссылки на раунды «до», «живой» и «после», итоги | Один семинар от идеи до измеренного эффекта |
| Registration | семинар, контакт или имя с почтой, клиент, статус, присутствие | Список участников и явка |
| Proposal | тип (шаблон, программа, приглашение, темы), содержимое, кто запросил, какая модель и промпт, статус, кто принял | Всё, что сделал ассистент, сначала лежит здесь. Полный след для аудита |
| AuditLog | кто, что, когда, над чем | То, что сейчас делает `hendingar.jsonl` |

Два правила, которые держат модель честной: Response никогда не ссылается на Contact или Registration, и любой запрос с разбивкой по роли проходит через один сервис, который применяет порог анонимности.

## AI-ассистент

Ассистент — не чат сбоку, а набор умений с типизированным результатом. Каждое умение возвращает JSON по схеме из `packages/schema`, сервер его проверяет и кладёт в Proposal. Чат в админке — только способ эти умения вызвать.

| Умение | Вход | Выход | Этап |
| --- | --- | --- | --- |
| Черновик опроса по брифу | «10 вопросов про бэкап для гостиницы, с двумя сценариями и советами» + стилевой гайд + примеры из библиотеки | TemplateVersion-черновик на языке брифа, с логикой и правилами советов | 2 |
| Редактура вопроса | один вопрос | замечания по стилю (жаргон, два вопроса в одном, наводящая формулировка) и вариант правки | 2 |
| Перевод версии | версия на одном языке + глоссарий терминов Vardahei | два недостающих языка как Proposal; версия не публикуется, пока носитель не принял | 2 |
| Краткое содержание свободных ответов | очищенные тексты одного вопроса по клиенту | темы с числом упоминаний и цитатами | 2 |
| Объяснение вывода | Finding + цифры | текст для встречи с клиентом, на нюношке | 2 |
| Темы семинаров из выводов | Findings по всем клиентам за период | 3–5 тем с доказательствами: какие клиенты, какие цифры | 4 |
| Пакет семинара | тема, аудитория, длительность, связанные выводы | приглашение, программа, план слайдов с заметками для ведущего, вопросы для живого опроса, опрос после семинара | 4 |

Как устроен модуль `assistant`:

- Адаптер модели с одним интерфейсом: структурированный вывод, инструменты, стоимость. Версия модели и промпта записывается в каждый Proposal.
- Инструменты только на чтение: библиотека вопросов, агрегаты по раунду, выводы, прошлые семинары, каталог Action. Запись только в Proposal.
- Знания в контексте, без векторной базы: стилевой гайд, глоссарий на нюношке, библиотека вопросов. Она маленькая, и так останется долго.
- Длинные задачи (пакет семинара) идут через очередь pg-boss, результат приходит в админку по SSE.
- Лимит стоимости в день и на пользователя, как в ai-verkstad.

Как проверяем качество, без этого ассистент не принимается:

1. Автоматические проверки каждого черновика опроса: схема валидна, в каждом закрытом вопросе есть «veit ikkje» или равноценный выход, нет названий продуктов из стоп-списка, длина вопроса до 25 слов, сценарий имеет правильный ответ и пояснение, оба языка заполнены.
2. Золотой набор: 10 брифов с ожидаемыми свойствами результата. В CI гоняется на записанных ответах модели, ночью — на живой.
3. Язык: для нюношка — список букмольских форм, которых не должно быть («ikke», «hva», «hvordan», «jeg»), для букмола — обратный список («ikkje», «kva», «korleis», «eg»), как дешёвый первый фильтр. Окончательно текст читает человек, и это остаётся шагом процесса, а не надеждой.
4. Статистика принятия: какая доля предложений принята без правок, с правками, отклонена. Это главный показатель пользы ассистента.

## Семинары

Семинар в платформе — не событие в календаре, а цепочка с измеримым результатом. Он рождается из выводов и заканчивается сравнением «до и после».

1. **Идея.** Ассистент или человек выбирает тему из выводов: «у четырёх клиентов половина людей не знает, что делать после клика на фишинг». Целевые клиенты подставляются сами.
2. **План.** Дата, формат (в Campus Sogndal, у клиента, Teams), ведущий, программа. Ассистент даёт пакет: приглашение, программа, план слайдов с заметками. Слайды делаются снаружи, платформа хранит файл или ссылку.
3. **Приглашение.** Страница регистрации с именем, компанией и почтой, файл ICS для календаря. Сначала текст отправляет человек, позже платформа через почту Vardahei.
4. **Проведение.** Экран ведущего с QR-кодом. Участники отвечают на вопросы с телефона через тот же раннер, результат появляется на экране сразу. Сценарий «письмо от начальника» в зале на 50 человек работает лучше любого слайда.
5. **После.** Участники получают материалы и короткий опрос. Через 2–3 месяца новый раунд по якорным вопросам показывает, сдвинулось ли что-то у клиентов, которые были на семинаре, по сравнению с теми, кто не был.

Здесь платформа даёт то, чего не даст календарь с рассылкой: тема с доказательствами, живой опрос без отдельного сервиса и честный ответ на вопрос «помог ли семинар».

## Процесс: кто что делает

Все договорённости живут в репозитории, в папке `docs/`: `ARCHITECTURE.md`, `adr/ADR-001.md` и далее, `STAGES.md`, `PRINCIPLES.md`, `REVIEW-CHECKLIST.md`. Любая сессия любой модели читает только их, а не историю чатов. Эти файлы на английском, потому что рядом с кодом.

1. **Brainstorm, раунд 1.** Astra получает этот документ и отвечает в жёстком формате: по каждому из 19 решений — «согласен», «меняю на X, потому что» или «не хватает Y»; не больше пяти новых решений; пять главных рисков. Вопросы из колонки «Вопрос к Astra» обязательны к ответу.
2. **Раунд 2.** Fable сводит: по каждому решению статус «принято» или «спор», для споров — два варианта с ценой каждого. Черновики ADR и `STAGES.md`.
3. **Раунд 3.** Astra делает последний проход только по спорным пунктам. Что осталось спорным, решает Oleksandr. Больше трёх раундов не бывает: дальше модели начинают соглашаться из вежливости.
4. **Пакет этапа.** Перед каждым этапом Fable пишет `stages/stage-N.md`: задачи по 1–3 часа каждая, критерии приёмки, обязательные тесты, что не входит. Astra проверяет пакет одним проходом.
5. **Код.** Opus 5.5 high работает по пакету в ветке `stage-N`, одна задача — один коммит с тестами. В конце — PR и `stages/stage-N-report.md`: что сделано, что отложено, где отступил от пакета и почему.
6. **Приёмка.** Sol и Opus 5.5 xhigh, каждый в чистой сессии, получают только репозиторий, `docs/` и пакет этапа. Они запускают тесты, читают diff и проверяют каждый критерий приёмки руками. Ответ — список замечаний с уровнем: блокирует, важно, мелочь. Отчёт кодера они читают последним, чтобы он не подсказывал, куда смотреть.
7. **Исправления.** Opus чинит блокирующее и важное. Повторное ревью только по изменённому коду, как вы уже делаете в Atlas.
8. **Готово.** Этап принят, когда у обоих ревьюеров нет блокирующих замечаний, CI зелёный и Oleksandr прошёл критерии приёмки сам на тестовом стенде. Только после этого — слияние и выкладка.

Два правила, которые экономят больше всего времени. Ревьюеры никогда не видят переписку с кодером, иначе они проверяют его рассказ, а не код. И спор между моделями решается не третьей моделью, а человеком, которому показали два варианта с ценой.

## Риски и принятые решения

Риски, которые я вижу сейчас:

- **Построим платформу, которой пользуются два раза в год.** Самый большой риск. Ответ — этап 1 сразу заменяет рабочий инструмент, а не строит новый рядом; семинары и ассистент идут после того, как команда провела через платформу хотя бы одну настоящую кампанию.
- **Нюношк у моделей.** Черновики на нюношке могут скатываться в букмол, а с тремя языками появляется и обратный риск: смешение внутри одного текста. Перед выбором модели — тест на десяти брифах с оценкой носителя; в CI — проверка, что язык ответа совпадает с запрошенным.
- **Анонимность при росте функций.** Каждый новый фильтр или экспорт — шанс случайно раскрыть одного человека. Поэтому порог сидит в одном сервисе, и ревьюеры проверяют его на каждом этапе по чек-листу.
- **Один VPS на всё.** Atlas, DnD-стек из десяти контейнеров, ai-verkstad, muligheter, теперь kartlegging. Клиентский сервис рядом с хобби-проектом — риск для репутации, если памяти не хватит в день семинара.
- **Entra требует админа тенанта Vardahei.** Без регистрации приложения этап 0 не закрывается.

Ответы Oleksandr от 11 октября и что они поменяли в документе:

1. **Админка — только трое.** Ролей нет: одна группа Entra, равные права (решение 8). Из этапа 0 ушла модель ролей — день-два работы и один слой сложности меньше. Если команда вырастет, роль станет атрибутом группы Entra, вход переписывать не придётся.
2. **До пяти семинаров в год.** Семинары остаются отдельным этапом 3: это главный повод для платформы. А автоотправку приглашений через Microsoft Graph убрали (решение 13): пять рассылок в год не окупают интеграцию с почтой и возню со спам-фильтрами. Этап 5 стал меньше и называется «Отчёты и хранение».
3. **Договор с Microsoft — неизвестно.** Насколько я знаю, отдельный договор для Azure OpenAI обычно не нужен: обработка данных покрыта стандартным Microsoft Products and Services DPA, который входит в условия любой подписки Azure. Проверить в этапе 0 надо четыре вещи: подписка оформлена на Vardahei, а не на клиента; ресурс создан в регионе ЕЭЗ (на момент написания самый полный набор моделей — Sweden Central, в Norway East их меньше); abuse monitoring — Microsoft может хранить промпты до 30 дней, отключение по отдельной заявке; и запись в реестре обработки (GDPR, ст. 30). Свободные ответы респондентов идут в модель только после очистки (решение 11), так что даже при 30 днях хранения туда не попадают имена.
4. **Букмол — да.** Новое решение 19: три языка с первого дня. Схема шаблона, раннер и язык по умолчанию у клиента — в этапе 1; букмол-версии двух текущих опросов — в этапе 2 через ассистента с проверкой носителя. Админка остаётся на нюношке.
5. **SaaS — нет.** Решение 14 закрыто с высокой уверенностью: одна организация, без `org_id`, вопрос к Astra снят. Это экономит неделю в этапе 0 и упрощает каждую таблицу.
