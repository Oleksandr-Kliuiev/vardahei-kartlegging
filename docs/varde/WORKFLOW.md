# Процесс работы Varde

Как идёт работа над этапами: роли моделей, ветки, коммиты, evidence, приёмка и merge. Источник правил — `docs/varde/PRINCIPLES.md` §19–22 и `docs/varde/STAGES.md` «Протокол checkpoint»; при расхождении прав PRINCIPLES (текст ниже — копия, тест `varde/tools/docs/test/workflow-matches-principles.test.ts` сверяет её дословно).

## Роли и усилия моделей

Копия PRINCIPLES §20:

**Роли и усилия моделей** (политика от 11.10.2026; копия в `docs/varde/WORKFLOW.md`): GPT-6.1 Sol (`medium`) — оркестрация и коммуникация («оркестратор (Sol)»: пины, merge; на VPS не ходит); GPT-6 Astra (`xhigh`) и Claude Fable 5.1 (`xhigh`) — архитектура, независимое одобрение каждого нового этапа и материальных изменений архитектуры по одному артефакту; Claude Opus 5.5 (`medium`) — код по пакету этапа: одна задача (1–3 ч) — один коммит с тестами; GPT-6.1 Sol (`xhigh`) и Claude Opus 5.5 (`xhigh`) — приёмка и ревью исправлений в чистых сессиях, по одному artifact hash, вход — только репозиторий + `docs/` + пакет этапа, отчёт кодера читается последним. Оркестратор (Sol) пинит модель и усилие на каждый запуск; исполнитель сообщает фактическую модель, усилие, fallback или несоответствие, и именованные ворота остаются pending при подмене. Никто из агентов не меняет provider routing, глобальные настройки моделей, billing или credentials ради выполнения задачи. Один писатель на checkout; дополнительные агенты — только по явному назначению с изолированной областью. Действия на хостинге (VPS, superuser-шаги на `atlas-db-1` через `docker exec … psql` внутри контейнера без чтения env Atlas, Caddy, сети Docker, cron бэкапа, деплой, uptime-monitor) выполняет хостинг-оператор (Claude Opus 5.5) с `ssh vardahei-vps` — в `docs/BESLUTNINGER.md` «Claude-оркестратор» — по runbook-шагам пакета этапа — команды, проверка, откат, вывод без секретов в evidence; кодер работает только в репо, CI и локально и не получает доступа к VPS и секретам; за Oleksandr остаются регистрации в Entra и доступ к SharePoint, DNS-запись, своя пара age; выпущенные им client secrets он вписывает в env на VPS сам (`stages/stage-0.md` §9 п. 14) (решение 13.10). Закрываются и blocking, и important замечания; повторное ревью покрывает затронутые инварианты, не только изменённые строки; после двух попыток починки без прогресса — возврат с диагнозом. **Изменено решением Oleksandr 13.10:** Fable и Astra — только в крайнем случае (спор по архитектуре или блокер, который иначе не закрыть); GPT-6.1 Sol не используется; оркестрация, пакеты этапов и хостинг — Claude Opus 5.5; приёмка checkpoint — одна чистая сессия Opus 5.5 (xhigh) плюс зелёный CI.

## Процедура

1. **Пакет этапа.** Этап начинается с одобренного пакета в `docs/varde/stages/` (`stage-N.md` и файлы checkpoint). Пакет входит в манифест одобренного артефакта (`stages/stage-0.md` §10); менять ARCHITECTURE, PRINCIPLES, STAGES, `adr/` и `stages/` может только автор пакета с повторным одобрением.
2. **Ветка на checkpoint.** `varde/<cp>` от `main` (например, `varde/0a`); зависимый checkpoint ветвится от `main` после merge предыдущего. Один писатель на checkout; второй исполнитель — только по явному назначению с отдельным worktree.
3. **Одна задача — один коммит с тестами.** Сообщение `varde 0.N: <что сделано>` по-английски или по-норвежски. Перед коммитом — `pnpm check` в `varde/` и тесты задачи; CI на коммите задачи зелёный.
4. **Инварианты.** Последняя задача checkpoint — его тесты инвариантов (`pnpm invariants:<cp>`); строки дописываются в `docs/varde/REVIEW-CHECKLIST.md`.
5. **Evidence.** Кодер пишет `docs/varde/evidence/stage-N/<cp>-evidence.md` по шаблону `stages/stage-0.md` §6: commit hash, манифест одобренного пакета и вычисленный на commit, команды приёмки с фактическим выходом, hash fixtures, отклонения, внешние входы, инварианты, фактическая модель и усилие, URL зелёного CI run. Evidence, отчёты и runbooks лежат вне манифеста.
6. **Push.** Кодер пушит ветку `varde/<cp>`; PR и merge в `main` кодер не делает.
7. **Приёмка.** Чистая сессия ревьюера по commit hash (состав ревьюеров — §20 выше, с изменением 13.10): вход — репозиторий, `docs/varde/` и пакет этапа; отчёт кодера читается последним. Ревьюер сверяет манифест на commit с одобренным и проходит `docs/varde/REVIEW-CHECKLIST.md`.
8. **Замечания.** Закрываются blocking и important; повторное ревью покрывает затронутые инварианты; после двух попыток починки без прогресса — возврат с диагнозом.
9. **Merge.** После приёмки merge в `main` делает оркестратор. Этап принят по PRINCIPLES §22.
