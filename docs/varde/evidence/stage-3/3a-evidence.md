## Что сделано

**3.1 Сущности и хранение.**
- Seminar: тема nn/en, начало и конец (instant в базе, Europe/Oslo везде на экране, в тексте и ICS), место, формат `onsite | digital`, клиенты (`seminar_client`), `required_languages ⊆ {nn, en}` с nn, код ссылки — 128 бит base64url, поиск по sha256 (как коды раундов, ADR-009), `sequence` для обновлений в календаре, nullable `round_before/live/after` (заполнит 3c).
- Contact: имя, e-post (trim + lower case, CHECK, unique), компания (имя клиента или свой текст) и `client_id?`, `role_at_client?`, необязательное согласие на приглашения `invite_consent_version/at` (решение 16.10, оба или ни одного — CHECK), `created_at`, `last_confirmed_at`, `review_flagged_at`.
- Registration: семинар, контакт, язык, версия и время обязательного согласия этой регистрации, `created_at`; unique (семинар, контакт) = «семинар + e-post».
- Публичная форма создаёт контакт, а у известного может только добавить согласие на приглашения (решение 16.10): ни имя, компанию и клиента, ни `last_confirmed_at` и отметку проверки она не меняет, согласие не снимает (вход без логина, e-post не подтверждается). Имя и компанию (или клиента) правит админ в «Namneliste» — `PUT /api/admin/contacts/:id`, AuditLog `seminars.contact.update` с именами полей без значений; новый год для контакта начинает только «Stadfest». «Fjern påmelding» удаляет одну регистрацию (AuditLog `seminars.registration.remove`); контакт без других регистраций и без согласия на приглашения уходит в ближайший прогон задачи, с согласием — остаётся до проверки или «Sletting».
- Action (name, description, seminar_topic) и связь FindingRule → Action — таблица `finding_rule_action (rule_key → action_id)` рядом с неизменяемыми версиями (решение ниже).
- FindingStatus: `open | in_seminar | closed`, `seminar_id?`, кто и когда; нет строки = `open`. Привязка Finding к семинару (`POST /api/admin/seminars/:id/findings`) ставит `in_seminar` с AuditLog `findings.status` — критерий приёмки 3.1 (тест `seminars.test.ts`).
- Инвариант ADR-021: у `response` один FK (`round_client`), нет колонок и триггеров про контакт, регистрацию, семинар; у `contact`/`registration` нет ссылок на ответы.
- Contact и Registration читает и пишет только `modules/privacy/participants.ts` (`PrivacyService.participants`); правило `varde/privacy-only-release` получило второй allow-list (модели `contact`, `registration`, `include`/`select`, raw SQL), selfcheck ловит обход.
- Retention (ежедневная задача 1.31, одна транзакция, dry-run, идемпотентно): регистрации удаляются через 90 дней после конца семинара; в том же прогоне — контакты без регистраций и без согласия на приглашения (решение 16.10, раздел ниже); остальным через год после создания или последнего «Stadfest» задача ставит `review_flagged_at`; админ видит отмеченных («Kontaktar» в разделе «Seminar», чтение под AuditLog) и нажимает «Stadfest» или удаляет. Журнал удаления по сроку — запись AuditLog `retention.run` со счётчиками всех классов, если что-то удалено или отмечено.
- Удаление по запросу: область `participant` в `retention.forget` и на «Sletting» («Deltakar på seminar (e-post)»): по нормализованному e-post удаляется контакт и все его регистрации; DeletionRequest с `scope_ref = {contact: <id>}` и ParticipantTombstone (id контакта, число регистраций) — без имени и e-post; AuditLog `retention.forget` со счётчиками; `ledger apply-db` после restore удаляет контакт снова. Dry-run (и для ответов) пишет AuditLog `retention.forget.preview`: кто и счётчики, без e-post, инициалов, клиента и основания.

**3.2 Регистрация.**
- `/s?c=<код>` — вторая страница сборки runner (Vite multi-page): те же токены Vardestien, шрифты, та же CSP и заголовки, что `/r`; внешних запросов нет (e2e это проверяет). Языки — `required_languages` семинара, нюношк по умолчанию; переключатель как в runner.
- Поля: имя, компания (радиокнопки клиентов семинара + «Anna bedrift» со своим текстом), e-post, согласие двумя галочками (решение 16.10, раздел ниже; полный текст — по «Les meir …»; версии приходят с сервера, тест фиксирует hash текстов каждой версии). Компанию выбирают по slug клиента — id базы публичный API не отдаёт. Скрытое поле «Nettstad» — honeypot.
- «Du er påmeld»: тема, дата, место, «Legg i kalenderen» (ICS), фокус на заголовок; переход — подъём контента (useEnter), первый экран после загрузки стоит на месте, как в опроснике.
- API без сессии, код только в `Authorization: Bearer` (никогда в query сервера): `GET /api/public/seminar`, `POST /api/public/seminar/registrations`, `GET /api/public/seminar/calendar`. Лимиты из `config/quotas.json`: `seminar_registrations_max` 300 на семинар (счёт в базе под блокировкой строки семинара, до проверки повтора), окна 10 минут `seminar_per_ip_per_10min` 20 (офис за одним NAT укладывается; один IP больше не заполняет семинар за полчаса) и `seminar_global_per_10min` 300 (память процесса). Повтор с тем же e-post и honeypot — тот же ответ `{registered: true}` без записи; неверный ввод — сообщение по полю, без сведений о других людях. Ошибки Prisma в лог не попадают (503 с общим текстом). Успешные запросы `/s` и `/api/public/*` не пишутся в лог, ошибки — только путь и статус.
- ICS: VCALENDAR/VEVENT, UID `seminar-<id>@<host>`, DTSTAMP, DTSTART/DTEND в UTC, SEQUENCE, SUMMARY, LOCATION, DESCRIPTION со ссылкой, URL; CRLF, folding по 75 октетам без разрыва UTF-8, экранирование. Тесты разбирают файл ical.js (dev-зависимость, точная версия 2.2.1).

**3.3 Материалы.** Заголовок и http(s)-ссылка (CHECK в базе), без загрузки файлов. Админ добавляет и убирает (AuditLog). `/s?c=` показывает материалы только после конца семинара — всем, у кого есть ссылка; до конца API их не отдаёт.

**3.10 Пакет приглашения.** Вкладка «Invitasjon»: письмо на нюношке (и английском, если он есть у семинара) — редактируемое, «Kopier tekst», ссылка с «Kopier lenkje», «Last ned invitasjon» (zip: `LES-MEG.txt`, `invitasjon.txt` / `invitation-en.txt`, `lenkje-til-pamelding.txt`, `seminar.ics` / `seminar-en.ics`, `plakat.html` / `plakat-en.html`), «Kalenderfil (ICS)», «Opne plakaten (A4)» (`/admin/poster/seminar/:id`, узкая CSP плакатов раундов). QR строит `qrcode-generator` 1.4.4 (уже был в зависимостях), логотип — data URI, ничего не грузится снаружи. Varde ничего не отправляет; скачивание — AuditLog `seminars.invitation` с префиксом hash кода.

**Админка.** Раздел «Seminar» в группе «Innhald» (иконка `folk`, после «Funn»): список (ближайшие сверху, потом прошедшие; дата, тема, время, место, клиенты, «N påmelde»), «Nytt seminar», карточка «Kontaktar» (ежегодная проверка), страница семинара с «Endre» и вкладками «Påmelding» (число по клиентам, ссылка, «Ny lenkje» в два нажатия с предупреждением, «Vis namnelista» — список по запросу под AuditLog, в строке «Endre» контакта и «Fjern påmelding»), «Materiell», «Invitasjon», «Live» и «Før og etter» — «Kjem i neste steg». SSE-тема `seminars` обновляет счётчики сразу после регистрации.

**Ny lenkje (ADR-009).** `POST /api/admin/seminars/:id/reissue`: новый код, старый hash — в `revoked_seminar_code`; старая ссылка, отправленные приглашения, плакаты и ссылки в календарях участников сразу дают «Lenkja er bytt ut» (отдельный экран на `/s`). AuditLog `seminars.code.reissue` с префиксами hash, без кода.

## Согласие двумя галочками (решение 16.10)

Коммиты `5469002` (форма, API, админка, тесты, e2e) и `97e42bb` (retention контактов); миграция `20261016120000_seminars` правлена на месте (не выкачена).

- **Форма `/s?c=`** — две галочки в одной рамке (legend «Samtykke» для скринридера):
  1. обязательная: «Eg samtykkjer i at Vardahei IT lagrar namnet, bedrifta og e-postadressa mi for denne påmeldinga.» — версия `pamelding-v1` и время на Registration (`consent_version`, `consent_at`);
  2. необязательная, по умолчанию снята: «Eg vil gjerne få invitasjon til seinare seminar frå Vardahei IT. (valfritt)» — версия `invitasjon-v1` и время на Contact (`invite_consent_version`, `invite_consent_at`, CHECK «оба или ни одного»). Поле `invite` уходит в запросе, только если галочка отмечена (e2e смотрит тело запроса).
- **Без обязательной галочки** страница не отправляет форму: «Kryss av for at vi kan lagre opplysningane for påmeldinga, så kan du melde deg på.», фокус на галочку. API отвечает 400 с тем же текстом — одинаково для нового и известного e-post, т. е. не раскрывает, есть ли человек (тест). Старая или чужая версия любой галочки — 409 «Teksten om personvern er endra …», лишний тип — 400.
- **Известный контакт.** Отмеченная вторая галочка добавляет согласие, если его ещё нет, — больше форма у контакта ничего не меняет (тест сравнивает строку контакта целиком: имя, компания, клиент, `last_confirmed_at`, отметка проверки); снятая галочка согласие не снимает. Снять можно только «Endre kontakten» → «Ta bort samtykket til invitasjonar» (AuditLog `seminars.contact.update` с полем `invite`, без значений) или «Sletting». Дать согласие за человека админ не может: API знает только `withdraw_invite`, поле `invite` — 400.
- **«Les meir»** — пять пунктов под обе цели: что храним и зачем; регистрацию удаляем через 90 дней, без галочки приглашений тогда же удаляем имя и e-post (если нет другой регистрации); с галочкой храним, пока человек хочет приглашения, список проверяем раз в год; в отчёты не попадает и никому не передаётся; отказаться от приглашений, посмотреть или удалить — post@vardahei.no. Hash текстов закреплён для каждой версии (`texts.test.ts`); «Les meir» входит в обе, его правка = две новые версии.
- **Хранение (1.31).** Ежедневная задача в той же транзакции после удаления регистраций удаляет контакты без регистраций и без согласия на приглашения: тех, чья последняя регистрация истекла, и тех, кого оставили без регистрации «Fjern påmelding» или снятие согласия админом. Журнал — счётчик `contact` в AuditLog `retention.run`; dry-run считает и ничего не пишет; повторный прогон — 0. Каждый контакт удаляется под advisory lock своего e-post с повторной проверкой после блокировки: регистрация, сделанная в ту же секунду, иначе ушла бы каскадом вместе с контактом — тест «a registration made while the job runs keeps its contact» (без блокировки падает, проверено мутацией). С согласием контакт живёт до ежегодной проверки или «Sletting». `docs/varde/RETENTION.md`, строка `contact`: «пока есть согласие на приглашения или активная регистрация; проверка раз в год». `config/retention.json` не менялся (`contact: relationship, review yearly`).
- **Админка.** «Namneliste» — колонка «Invitasjon» (ja/nei); кнопки «Endre» и «Fjern påmelding» встают друг под другом, когда колонкам тесно (с новой колонкой на 1280 px вторая кнопка обрезалась). «Endre kontakten»: галочка «Ta bort samtykket til invitasjonar» только у тех, у кого согласие есть, иначе — «Personen har ikkje sagt ja til invitasjonar.». Карточки «Påmelding» и «Kontaktar» говорят новое правило.
- **Тесты.** Integration (`participants.test.ts`, `registration.test.ts`): только обязательная → согласия на приглашения нет; с необязательной → есть; известный контакт — форма добавляет, но не снимает и больше ничего не меняет; админ снимает (AuditLog), дать не может; retention — контакт без согласия удаляется вместе с последней регистрацией через 90 дней, с согласием или с другой регистрацией остаётся, dry-run ничего не пишет, второй прогон 0, гонка с регистрацией; «Fjern påmelding» → контакт без согласия уходит в следующий прогон, с согласием остаётся; без обязательной галочки → 400 (и для известного e-post). Unit: runner (две галочки, вторая снята, тело запроса), admin (колонка, снятие, нет галочки «дать»), `texts.test.ts` (hash обеих версий, точные тексты галочек, нюношк без букмола). e2e runner: две галочки на nn и en при 360 и 1280 px, вторая снята; без обязательной — текст и фокус; тело запроса без `invite` (nn) и с `invite` (en). e2e admin: регистрация с обеими галочками → «ja» → снятие в «Endre kontakten» → «nei», и после перезагрузки страницы.

## Отклонения и решения

1. **FindingRule → Action** — таблица `finding_rule_action (rule_key PK → action_id)`, а не `action_id` в definition: версии правил неизменяемы (триггер), связь действует на все версии ключа, её смена не пишет новую версию (AuditLog `findings.rule_action`). UI для Action и привязки Finding в 3a нет — только API и тесты; естественное место — «Funn» и 4.1.
2. **Участники в модуле privacy.** Требование «выдача строк только через privacy» распространено на Contact и Registration: `participants.ts` — единственный файл с доступом (lint с отдельным allow-list, чтобы этот файл не получил доступ к Response). Отчёты, экспорт, архив, дашборд, ассистент и будущий Atlas физически не могут читать участников.
3. **«Семинар + e-post»** = unique (seminar, contact) + unique `contact.email`. Контакт общий для семинаров. Публичная форма известный контакт не меняет (замечание приёмки): ни имя, компанию и клиента, ни `last_confirmed_at` и отметку проверки; единственное исключение (решение 16.10) — отмеченная галочка добавляет согласие на приглашения, которого ещё нет; обязательное согласие каждой регистрации хранится на ней самой. Повтор на тот же семинар — тот же ответ без записи. Опечатку в имени или компании исправляет админ («Endre» в «Namneliste»).
4. **`role_at_client`** есть в модели (ARCHITECTURE), но на публичной странице не спрашивается: в задании четыре поля, минимизация данных.
5. **Компания хранится у контакта**, не у регистрации (модель ARCHITECTURE). В счётчиках раздела — только клиенты Varde, введённые участниками названия идут как «andre»: всё, что ввёл человек, видно только в списке под AuditLog. Если человек позже записался от другой компании, контакт остаётся с прежней (форма его не меняет), пока админ не поправит.
6. **Журнал удаления по сроку** — AuditLog `retention.run` со счётчиками (у существующих классов журнала не было; tombstone для таймерных классов не пишутся — ADR-017: после restore задача удаляет те же строки снова). AuditLog живёт 12 месяцев.
7. **Ежегодная проверка контактов**: в `retention.json` у `contact` добавлено `review: yearly`; отметка ставится через год после `last_confirmed_at` (создание контакта или «Stadfest»); новая регистрация и правка админом её не снимают.
8. **Регистрация открыта до конца семинара** (`ends_at`); после — 410 «Påmeldinga er stengd.» и фаза «Seminaret er over» с материалами.
9. **Календарь на публичной странице** скачивается `fetch` с bearer и сохраняется из памяти (blob): код не попадает в URL, который видит сервер. На iPhone Safari файл, скорее всего, уйдёт в «Файлы», а не сразу в «Календарь» — не проверено на устройстве.
10. **ICS в UTC** без VTIMEZONE (разрешено заданием); Outlook и телефоны показывают местное время.
11. **Страница `/s` — часть сборки runner**, а не отдельное приложение: те же токены, CSP и движение; ассеты по `/r/assets/`.
12. **Согласие** — две галочки по решению Oleksandr 16.10 (было: одна на регистрацию и приглашения) — раздел ниже.
13. **Время семинара в форме** — один день (дата, «Frå», «Til»); многодневный семинар модель умеет, форма — нет.
14. Тестовая поддержка `resetImports` теперь удаляет и `participant_tombstone` (она чистит все запросы удаления).
15. **Плакат** — по адресу `/admin/poster/seminar/:id` под исключением CSP плакатов раундов в `admin/static.ts`.
16. **Миграция `20261016120000_seminars` правлена на месте** после приёмки (она ещё не выкачена): согласие на `registration`, таблица `revoked_seminar_code`; 16.10 — у `contact` согласие на приглашения вместо согласия создания. `down.sql` дополнен, `migrations.test` зелёный; все локальные базы пересозданы с нуля.
17. **История заменённых кодов семинара** (`revoked_seminar_code`) — только hash, без персональных данных, живёт вместе с семинаром (как `revoked_round_code` у раундов).
18. **Dry-run удаления ответов** тоже пишет `retention.forget.preview` — это одна запись в той же транзакции, дёшево; дополнительно проверено в `forget.test.ts`.

## Приватность и риски

- Contact и Registration — персональные данные (ADR-017): только админ-сессия; список семинара и список «на проверку» пишут AuditLog `privacy.participants` (кто, семинар, число) в той же транзакции; в AuditLog, журнале удалений и логах нет имён и e-post (тесты). Обход всех зарегистрированных маршрутов с синтетическим участником (`3a-participants.test.ts`) находит его только в двух каналах.
- Нет подтверждения e-post (автоотправки почты нет — решение 11.10 в `docs/BESLUTNINGER.md`, строка «автоотправку через Microsoft Graph не делаем»): человек со ссылкой может записать на семинар чужой адрес. Если адрес новый — появится контакт с введёнными данными (без согласия на приглашения он уйдёт сам через 90 дней после семинара); если известный — меняется список регистраций, а у контакта форма может только добавить согласие на приглашения. Значит, чужой человек может «подписать» известный адрес на приглашения; Varde писем не отправляет, приглашения шлют вручную, снять согласие — «Endre kontakten». Лишнюю регистрацию админ убирает «Fjern påmelding», контакт — «Sletting».
- Основание «Grunngjeving» при удалении — свободный текст и хранится в журнале бессрочно; страница просит не писать туда имя и e-post.
- Разница во времени ответа между новой регистрацией и повтором (лишние записи в базу) — незначительный побочный канал.
- Реестр обработки (`docs/varde/personvern/behandlingsregister-varde.md`) не содержит записи о регистрации на семинары — нужен текст.
- Операционная заметка: при остановке своего временного сервера проверки вёрстки я один раз выполнил `pkill -f "node dist/main.js"` — это могло остановить чужой локальный dev-сервер с той же командой; дальше останавливал только по PID.
