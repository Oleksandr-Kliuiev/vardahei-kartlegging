## Что сделано

**3.4 Live poll и presenter-ключ.**
- Живой опрос — раунд `type = live` с опубликованной версией шаблона `audience = seminar_live`, `identification = none`; привязка — `seminar.round_live_id` из 3a (частичный уникальный индекс: один семинар на live-раунд; триггер: это раунд типа `live`). Население — весь семинар: один RoundClient на семинар (ADR-022) и один код/ссылка `/r?c=…`, без разбивки по клиентам (решение 1 ниже).
- Создаёт админ во вкладке «Live» (`POST /api/admin/seminars/:id/live`): версия проверяется (`live-template.ts`: только вопросы с одним или несколькими вариантами, общая часть, без свободного текста, условий и `choices_from`, без инициалов — иначе 400 с понятной причиной); раунд сразу `open`, код ссылки живёт до конца окна ключа и сдвигается вместе с переносом семинара. Пока ни один вопрос не открыт, опрос можно убрать («Ta bort live-spørsmåla», ключ отзывается).
- Состояние вопроса — `live_poll_question.state`: `waiting → open → closed → released`, `closed → open` до показа, `released` окончательно (решение 2); один открытый вопрос. Шаги ведёт сервер (`LivePollService.step`) под блокировкой строки раунда — той же, что берёт отправка ответа; повтор того же шага (двойной клик) — без изменений; недопустимый — 409 с текстом. База отказывает так же: триггер `live_poll_question_step` (вставка только `waiting`, только разрешённые переходы, идентичность строки не меняется) и частичный уникальный индекс «один `open` на раунд». Каждый шаг — AuditLog `seminars.live.open/close/release` (`target round:<id>`, детали — id и номер вопроса; `who` — админ или `presenter:<id ключа>`).
- Ответы — обычные Response через `POST /api/runner/submissions` (ADR-006: тот же контракт, идемпотентность, журнал удалений): одна отправка — один вопрос, общая часть, без роли и свободного текста, без `respondent_key`. Проверка в транзакции после блокировки раунда: вопрос должен быть `open`; закрытый → 409 «Spørsmålet er stengt.», ещё не открытый → 409 «Spørsmålet er ikkje ope enno.»; повтор уже сохранённого ответа (потерянное подтверждение) отвечает 201 и после закрытия. Квоты — свои (решение 9).
- Presenter-ключ (ADR-008): 256 бит (43 символа base64url), в базе только sha256 (CHECK `^[0-9a-f]{64}$`); показывается один раз ссылкой `/p#t=<ключ>`; к API — только `Authorization: Bearer`. Окно — с 00:00 дня до семинара до 24:00 дня после (Europe/Oslo, по текущим датам семинара; летнее время учтено). Один активный ключ на семинар (частичный уникальный индекс): новый отзывает старый; «Trekk tilbake» в админке. Выпуск и отзыв — AuditLog `seminars.presenter.issue/revoke` с id строки и префиксом hash, ключа нет ни в базе, ни в журнале, ни в логах. Нет ключа / чужой формат / неизвестный → 401, отозванный или вне окна → 403.
- Область ключа: `GET /api/presenter/poll`, `POST /api/presenter/questions/:q/open|close|release`, `GET /api/presenter/stream` — только своего опроса (в маршрутах нет id семинара или раунда: опрос определяет ключ). Обход всех маршрутов (`3b-presenter-routes.test.ts`): на остальных ответ с ключом совпадает с ответом без него, на `/api/*` — 401/403.
- Цифры только через `PrivacyService.live` (`privacy/live.ts`; чтение `response` — `liveAnswered`/`liveCounts` в `prisma-source.ts` из allow-list lint): «N har svart» открытого или закрытого вопроса — с k = 3, как счётчики прогресса админки (приёмка 16.10, вариант b): от трёх ответов число, меньше — `{suppressed: true}` и на экране «Færre enn tre har svart»; результат — только у вопроса в состоянии `released` (состояние читается в той же функции), класс `aggregate` с k = 3: меньше трёх ответов — `{suppressed: true}` без чисел, и счётчик у показанного вопроса пропадает (`null`). Квота live-ответов спрашивает privacy только «полон ли вопрос» (`live.full`), числа не получает.

Внизу управление ведущего: номера вопросов (выбор), «Opne», «Steng», «Vis» по состоянию выбранного вопроса; повторный клик во время запроса игнорируется.

- SSE (ADR-015): `GET /api/presenter/stream`, один поток на экран ведущего и опрос. Каждое событие — целый snapshot (тексты, состояния, счётчик, результат после privacy, ссылка и QR для телефонов); первое событие — snapshot текущего состояния, в том числе после reconnect; изменения (шаг, ответ, отзыв ключа) толкают новый snapshot с дебаунсом 200 мс; ключ перепроверяется на каждом push и ping (20 с), отзыв или конец окна закрывают поток (`event: ended`). Клиент читает поток через `fetch` (EventSource не умеет заголовок Authorization), переподключается через 1 → 15 с; после `ended` сразу спрашивает ещё раз, чтобы показать причину сервера («trekt tilbake» и т. п.).
- Вкладка «Live» в админке (эталон `semKropp`): карточка «Live-spørsmål» с цепочкой «Ope → Stengt → Vist», «N har svart · M påmelde», кнопками «Opne spørsmålet», «Steng spørsmålet», «Vis resultatet», «Opne igjen», «Opne neste spørsmål» и списком вопросов; справа — настоящая страница `/p` в рамке 1280 × 720, уменьшенная до карточки (данные — postMessage со страницы админки, без ключа); «Lenkje til mobilane»; «Nøkkel til storskjermen» (ссылка один раз, «Kopier», «Opne storskjermen», «Lag ny lenkje» и «Trekk tilbake» в два нажатия, срок действия словами). Без опроса — выбор версии и причины, почему другие версии не подходят. Обновление — по SSE-теме `live` админки.

**3.6 Runner в live-режиме.**

## Нагрузочный тест (3.7)

Пересмотрено по решению 13.10: пика нет, реальный семинар — десятки человек. Скрипт поднимает собранный API (`apps/api/dist`) на одноразовой базе с синтетическим семинаром сегодняшнего дня, live-опросом и ключом; N «телефонов» с одного IP (`X-Forwarded-For: 203.0.113.50` — весь зал за одним NAT) отвечают на открытый вопрос в случайный момент за S секунд и до ответа опрашивают состояние раз в 2,5 с, как страница; экран ведущего держит SSE-поток. Потом вопрос закрывается и показывается. Провал, если p95 ответов ≥ 1 с, есть 429, не все ответы 201 или показанный результат считает не все ответы. ## Решения и отклонения

1. **Население «весь семинар» при `round_client.client_id NOT NULL`.** ADR-022: «Round типа live с одним RoundClient на семинар», а RoundClient требует клиента. Вместо nullable `client_id` (≈40 правок в privacy, метриках, дашборде, экспорте и журнале удалений) — один технический клиент `client.kind = 'seminar'` (`varde-seminar-live`, «Seminar (live)»): CHECK и частичный уникальный индекс (не больше одного), триггер `round_client_live` (технический клиент ⇔ раунд `live`), `kind` и `round.type` не меняются (триггеры). Технический клиент скрыт не только в интерфейсе, но и в API (замечание приёмки): его нет в `/api/admin/clients`, и каждый выбор клиента проверяет `kind = 'client'` — создание и правка семинара (400), правка контакта (400), запуск раунда и добавление клиента в раунд (400 до триггера, без ошибки Prisma в журнале), handover (404), удаление по клиенту и по человеку у клиента (400), `PUT/PATCH /api/admin/clients/:id` (404). Live-раундов нет в `/api/admin/rounds`, а по явному id дашборд (и сравнение), строки и цитаты, ответы руководителей, CSV, анализ, архив, прогресс, отчёт клиенту, приглашение и плакат отвечают 404 (проверка `type = 'live'` в `DashboardContext.load`, `progressView`, отчёте, архиве и приглашении); админка раундов на live-раунд отвечает 409. После отката миграции технический клиент останется обычной строкой (записано в down.sql).
2. **Повторное открытие** — `closed → open` разрешено, пока результат не показан; `released` окончательно. Так ведущий может исправить слишком ранний «Steng», а показанное число никогда не меняется от нового ответа (нет вычитания между двумя показами на экране). Эталон после «Vis» предлагает «Start på nytt» — его нет.
3. **Один открытый вопрос**: открыть второй — 409 «Spørsmål N er ope. Steng det før du opnar eit nytt.» (без неявного закрытия).
4. **Типы вопросов**: только один/несколько вариантов без свободного текста, общая часть, без условий; текст, шкала и NPS на экране не показываются — версия с ними не принимается при создании опроса (причина видна в админке). Вопрос роли, обязательный по схеме шаблона, в live — обычный вопрос с вариантами.
5. **Чтение ключом**: ADR-008 называет «чтение released-результатов»; ключ также читает то, что зал и так видит на экране: тексты и состояния вопросов, «N har svart» (с k = 3, решение 7), ссылку и QR для телефонов. Ничего другого.
6. **Released не хранится снимком**: результат считается при чтении, а входы заморожены (ответ на закрытый вопрос отклоняется, `released` окончательно). `AggregateSnapshot`/`privacy.release()` для live не используются: метрики раунда и снимки ADR-021 — для анкет; удаление отдельных live-ответов по запросу невозможно (нет ключа человека).
7. **Счётчик** «N har svart» (замечание приёмки, решение оркестратора 16.10 — вариант b) — через `privacy` с k = 3, как счётчики прогресса админки: при n ≥ 3 — число, при n < 3 — `{suppressed: true}` и текст «Færre enn tre har svart» (en: «Fewer than three have answered»), у открытого и закрытого вопроса; у показанного вопроса счётчика нет (`answered: null`). Ниже k не уходит ни одно число — ни в snapshot, ни в поток, ни в админку. Было: точный счётчик как исключение ADR-021 п. 6.
8. **Админ-карточка** показывает «N har svart» и результат только после «Vis» — как экран; в эталоне карточка админки показывает живые числа по вариантам во время открытого вопроса (ноутбук ведущего часто на проекторе). Нужно согласие Oleksandr.
9. **Квоты live** — новые ключи `live_*` (см. нагрузку); ADR-009 «по числу вопросов × участников» = не больше `live_participants_max` на вопрос (настраивается). Повторные ответы с одного устройства (очищенное хранилище, другой браузер) не блокируются — принятый остаточный риск (решение приёмки 16.10): live-опрос анонимный и неформальный, потолок на вопрос ограничивает накрутку.
10. **Цепочка состояний** — «Ope → Stengt → Vist», как в эталоне (`stengt` согласуется со «spørsmålet»); в задании было «Stengd».
11. **Короткая ссылка**: отдельного короткого кода нет (ADR-009: код ≥ 128 бит); на экране ссылка без `https://`, моноширинным шрифтом, и QR.
12. **SSE через fetch**, не EventSource: иначе ключ пришлось бы класть в query или cookie.
13. **`/api/runner/live` и `{type: 'live'}`** в `/api/runner/round` вошли в коммит 3.4 (серверная часть телефона рядом с проверкой ответа), интерфейс телефона — 3.6. Прогресс (`/api/runner/progress`) для live-кода — 409: у live нет пути по анкете.
14. **Журнал запросов**: `/p` и `/api/presenter/*` пишутся (метод, путь, статус — ключа в пути нет); `/api/runner/live` при успехе не пишется, как остальные маршруты runner.
15. **Экран ведущего** — полноэкранный вариант «Storskjerm» эталона: текстовая колонка прижата к верху (вопрос не прыгает), светлая и тёмная тема по токенам (в эталоне карточка экрана всегда тёмная), на 1280 × 720 помещается без прокрутки, на телефоне прокручивается.
16. **Лимит строк**: `apps/api/prisma/schema.prisma` — 569 строк (> 500, предупреждение `pnpm budget`; было 522 до 3b); разбивать Prisma-схему на папку — отдельная инфраструктурная правка. `privacy.service.ts` — ровно 500.
17. **Тестовые шаблоны** `seminar_live` (опубликованные версии неизменяемы) остаются в тестовых базах, как у других тестов.
18. **Откат и повторное применение миграции** (замечание приёмки): `down.sql` оставляет строку технического клиента (на неё ссылаются live-раунды) обычным клиентом; миграция `20261016140000_live_poll` (ещё не выкачена, правлена на месте) сразу после добавления `kind` возвращает этой строке, найденной по slug `varde-seminar-live`, `kind = 'seminar'`. Выбран этот путь, а не удаление live-раундов в `down.sql`: ничего не теряется. Тест `live/migration-rollback.test.ts` на своей базе: опрос → down → up → новый опрос на том же клиенте (без UPDATE падает).
19. **Ключ в выводе**: тесты ведущего и потока перехватывают всё, что пишет приложение, включая console (Vitest забирает console в своих воркерах, поэтому у `captureOutput` есть `{ console: true }`), и в конце проверяют, что в выводе нет ни одного ключа: ни выданного в тестах, ни любого 43-символьного окна, чей sha256 есть в `presenter_token`. Мутант «console.log ключа в `issue()`» обе проверки роняют.

## Приватность и риски

- Live-раунд анонимный: `identification = none`, триггер базы не пускает `respondent_key`; один вопрос на отправку — ответы одного человека на разные вопросы не связаны; IP и время дальше дня не хранятся (как у анкет).
- Экран ведущего — публичная страница с ключом; ключ не попадает в логи (Caddy без access log, фильтр ошибок удаляет Authorization; журнал приложения — без query и заголовков), запросы и Referer (fragment, `no-referrer`). Риск: ключ лежит в sessionStorage вкладки ведущего и в истории буфера обмена у того, кто его скопировал — срок окна и «Trekk tilbake» ограничивают его.
- Остаточный риск «потерянная ссылка ведущего на проекторе»: адресная строка ключ уже не показывает; но кто сфотографирует ссылку в админке — получит управление вопросами этого опроса до конца окна (данных людей ключ не открывает).
- Ссылка для телефонов общая для зала (как общая ссылка анкеты): один человек может ответить с нескольких устройств или повторно после очистки хранилища — принятый остаточный риск (решение приёмки 16.10, решение 9); квота на вопрос ограничивает накрутку.
- CI не запускался (GitHub Actions заблокирован лимитом расходов 16.10); push не делался.
