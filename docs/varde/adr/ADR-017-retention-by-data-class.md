# ADR-017: Хранение и удаление по классам данных

Статус: Accepted (решения Oleksandr 12.10: ответы хранятся бессрочно; при уходе клиента остаются; удаление — только по явному запросу под AuditLog). Изменено delta 12.10: спор 17 закрыт, варианты A/B для ответов сняты; добавлен механизм удаления по запросу; 13.10 — databehandleravtale покрывает опросники, по требованию клиента Vardahei возвращает или удаляет его данные; остаточный риск — текст обещания респондентам (0.18).

## Контекст
Раунд 2 brainstorm: Fable — сырые ответы 18 месяцев, Astra — 90 дней после закрытия раунда; варианты A/B и правило выбора. 12.10 Oleksandr решил: ответы обоих опросников, включая свободный текст и часть руководителя, по таймеру не удаляются; когда клиент уходит, его инициалы и ответы остаются — не удаляются и не обезличиваются. Это заменяет варианты A и B и формулировку «договор + 3 месяца» (`docs/personvern.md`). Ответы опросника по безопасности с 12.10 — персональные данные (инициалы, ADR-025), поэтому права субъекта (доступ, удаление по запросу) и решение клиента как behandlingsansvarleg по ст. 28(3)(g) этим решением не отменяются: нужен механизм удаления по явному запросу — по клиенту и по человеку. 13.10 Oleksandr и Asbjørn подтвердили: databehandleravtale покрывает опросники; клиент — behandlingsansvarleg, Vardahei — databehandlar; по требованию клиента Vardahei возвращает или удаляет его данные. Факты раунда 2 остаются верными: набор метрик раунда фиксируется при первом release (ADR-021), поэтому хранение raw не даёт новых опубликованных разрезов по выпущенному раунду; пересчёт тех же метрик после исправления ошибки — superseded release того же набора.

## Принято
- Снимки (`AggregateSnapshot`) содержат все распределения по вопросам × RoundClient × роль (с подавлением) и все метрики, включая кросс-вопросные и метрики зон (ADR-026); агрегаты, FUNN и тренды считаются из снимков и переживают удаление raw (тест полноты 1.11 для класса `aggregate`); канал `rows` (ADR-025) считается из raw и исчезает вместе с ним — ожидаемо.
- Новые метрики применяются только к раундам без release (ADR-021, правило 4); новые ретроспективные разрезы по выпущенному раунду — вне scope.
- Ответы (common и leader, закрытые и свободный текст, оба опросника, импортированные раунды) хранятся **бессрочно**. Задач удаления по таймеру и по окончании договора нет.
- **Удаление по явному запросу** (`retention.forget`): действие человека из админки с указанием основания. Область: `client` — все Response его RoundClient по обоим опросникам, обе части, свободный текст; `respondent` — `client` + `respondent_key` в идентифицированных раундах, обе части (ADR-025: leader несёт тот же ключ); `submissions` — явный список `submission_id`, найденный человеком, для строк без ключа: ответы анонимного KI-опросника, которые заявитель опознаёт по своему свободному тексту, и строки руководителя в анонимном раунде (их находит админ в классе `rows` или leader-эндпоинте, ADR-025). Released-снимки остаются (агрегаты под k). **Журнал удалений `DeletionLedger`**: запись запроса (кто, основание, область, когда) и tombstone на каждую удалённую строку (`submission_id`, `content_hash`, round, client, part; `source_id` у импортированной common-части; `respondent_key` в идентифицированных раундах) создаются в одной транзакции с удалением; dry-run показывает объём; повтор идемпотентен. Журнал — защита от возвращения удалённого: импорт (ADR-024) при любом прогоне подавляет common по `source_id`, а leader — по тройке `(round, client, content_hash)` из leader-tombstone, независимо от того, есть ли другая часть в базе (`suppressed`); `source_id` — постоянный `id` строки `svar.jsonl` (для раунда 1 — ключ записи), а не hash содержимого, поэтому identity переживает очистку при rollback; все пути возврата и их подавление — таблица в ADR-024 («Пути возврата удалённого»); rollback cutover применяет журнал к восстановленному архиву — `svar.jsonl` и `runde1.js`: строка или запись целиком по `source_id`, часть руководителя по `content_hash`, который импорт считает из части `leiardel` строки той же нормализацией (ADR-024, шаг 5); restore из бэкапа (ADR-016) всегда заканчивается применением журнала, а сам журнал экспортируется отдельным зашифрованным файлом сразу после каждой записи и из старого дампа не берётся — только последний экспорт, при расхождении объединение. Обезличивание (снятие `respondent_key` с сохранением ответов) не реализуется — при необходимости отдельный ADR.
- **Возврат данных клиенту по требованию** (`retention.handover`, решение 13.10): Vardahei как databehandlar по письменному требованию клиента (behandlingsansvarleg) выдаёт все данные клиента — строки обоих опросников через класс `rows` (в идентифицированных раундах с инициалами, ADR-025), строки руководителя и released-снимки — одним зашифрованным файлом уполномоченному лицу клиента, вне продукта; действие человека с основанием, запись в AuditLog (кто, клиент, объём, когда, кому передано); затем, если клиент требует, удаление через `retention.forget`. Автоматического канала у клиента нет; в продукте для клиента остаётся только `aggregate`.
- Задачи удаления для классов со сроком (ProgressEvent, Proposal, AuditLog, Registration, Contact) — ежедневные, с dry-run, идемпотентны, повторяются после восстановления из бэкапа.
- Backup-копии: версии в SharePoint живут 35 дней; корзина SharePoint может держать удалённое ещё до 93 дней. Задача 0.10 либо подтверждает фактическое исчезновение (политика purge корзины для библиотеки бэкапов, проверено в drill), либо реестр 0.19 записывает честный эффективный максимум = 35 + 93 дня после удаления. Для удалённого по запросу это и есть срок исчезновения из всех копий.
- Часть руководителя живёт по тому же правилу, что остальные ответы; она помечена конфиденциальной и выдаётся по правилу (a) ADR-021.
- Импортированные данные kartlegging: raw в Varde (раунд 1 из `runde1.js`, раунд 2 из `svar.jsonl`) — бессрочно, как остальные ответы; `svar.jsonl` и `private/runde1.js` выносятся из старого приложения в зашифрованный архив в момент cutover (старое приложение не хранит и не отдаёт raw); архив удаляется после отчёта клиентам, но не позднее 90 дней после cutover (задача 1.36) — третьего срока («не позднее удаления raw в Varde») больше нет. Копии раунда 1 вне Varde (`runde1.js` в приватном git, `Master_Analyse.xlsx` вне git) — владелец Oleksandr; реестр 0.19 перечисляет их с процедурой ручной чистки: при удалении из раунда 1 Varde выдаёт tombstone (hash записи), и Oleksandr удаляет запись из копий; история git — остаточный риск, решение о её перезаписи или удалении файла из репозитория после cutover за Oleksandr.
- Уведомление респондентам v2 (0.18) называет критерий хранения вместо срока: ответы хранятся, пока Vardahei IT ведёт kartlegging, и удаляются по запросу; роли сторон (клиент — behandlingsansvarleg, Vardahei — databehandlar) и право клиента требовать возврата или удаления всех данных; точную формулировку на нюношке утверждает Oleksandr.

## Остаточный риск: обещание респондентам против права клиента на возврат
Решение 13.10 даёт клиенту право требовать возврата всех его данных, включая строки по человеку с инициалами. Сегодняшнее обещание респондентам «Svara per person ser berre Vardahei IT. Bedrifta får eit samla bilete utan initialar» (kartlegging, 12.10) этого не предусматривает. Риск не скрывается, а снимается текстом: уведомление v2 (0.18) должно говорить, что Vardahei IT видит ответы по человеку, бедрифта в обычной работе получает только сводку без инициалов, но как behandlingsansvarleg может потребовать выдачи или удаления всех ответов; текст утверждает Oleksandr. До выхода нового текста возврат строк по человеку клиенту возможен только по письменному требованию с записью AuditLog, и Oleksandr решает, предупреждать ли респондентов текущего раунда отдельно. Ст. 5(1)(e): цель «сравнение от раунда к раунду» у действующего клиента; у ушедшего данные остаются по решению 12.10 до требования клиента об удалении или возврате — этот критерий назван в уведомлении (ст. 13(2)(a)).
