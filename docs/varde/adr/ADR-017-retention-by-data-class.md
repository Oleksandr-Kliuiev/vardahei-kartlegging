# ADR-017: Хранение и удаление по классам данных

Статус: **Proposed — спор 17**, решает Oleksandr. Правило выбора согласовано моделями в раунде 2 и уточнено после проверки одобрения (N1).

## Контекст
Fable: сырые ответы 18 месяцев. Astra: сроки по классам; закрытые ответы 90 дней после закрытия раунда; тренды хранят снимки. Факты: респондентам срок не обещан (только «не спрашиваем имя, малые группы — суммарно»); правило «удалить после отчёта» — внутреннее из README; из 21 правила FUNN кросс-вопросное одно (K7×K8), и оно сохраняется как метрика в снимке (ADR-020). По ADR-021 набор метрик раунда фиксируется при первом release, поэтому хранение raw **не даёт** новых опубликованных разрезов по уже выпущенному раунду.

## Принято обеими сторонами
- Снимки (`AggregateSnapshot`) содержат все распределения по вопросам × RoundClient × роль (с подавлением) и все метрики, включая кросс-вопросные; после удаления raw дашборд, FUNN и тренды считаются только из снимков (тест полноты в 1.11).
- Новые метрики применяются только к раундам без release (ADR-021, правило 4). Публикация новых ретроспективных разрезов по выпущенному раунду потребовала бы отдельного безопасного механизма (контроль раскрытия по всем прошлым выдачам) — вне scope, в обоих вариантах.
- Задача удаления ежедневная, с dry-run отчётом, идемпотентна, повторяется после восстановления из бэкапа.
- Backup-копии: версии в SharePoint живут 35 дней; корзина SharePoint может держать удалённое ещё до 93 дней. Задача 0.10 либо подтверждает фактическое исчезновение (политика purge корзины для библиотеки бэкапов, проверено в drill), либо реестр 0.19 записывает честный эффективный максимум = срок класса + 35 + 93 дня.
- Текстовые поля внутри ответа руководителя живут по сроку свободного текста, закрытые — по сроку закрытых ответов; часть руководителя помечена конфиденциальной и выдаётся по отдельному правилу ADR-021.
- Импортированные данные kartlegging: raw в Varde живёт по сроку выбранного варианта от даты закрытия кампании; `svar.jsonl` выносится из старого приложения в зашифрованный архив в момент cutover; архив удаляется после отчёта, но не позднее 90 дней после cutover и не позднее срока удаления raw этого раунда в Varde (задача 1.36, зависит от варианта).
- Уведомление респондентам v2 называет точные сроки выбранного варианта.

## Что даёт хранение raw после первого release
Не даёт: новых метрик или разрезов, опубликованных через приложение по выпущенному раунду.
Даёт: (1) пересчёт **тех же** метрик после исправления ошибки импорта или расчёта — superseded release того же набора; (2) офлайн-анализ без публикации: в варианте 21A — только оператор out-of-band под журналом, в 21B — raw-экспорт с причиной и AuditLog. Не требуют raw и потому не аргумент: перепроверка Findings при изменении текста или порога FindingRule (считается по snapshot, ADR-020) и «запрос респондента по его данным» (Response не связана с человеком, PRINCIPLES §7).

## Цена
- A: окно для пересчёта тех же метрик и офлайн-анализа — 90 дней; дальше только снимки. Самое короткое окно псевдонимных данных.
- B: то же окно — 12 месяцев: расчёты метрик, исправленные после первой кампании, можно пересчитать по ней; год псевдонимных данных под `privacy`; срок в уведомлении. Стоимость реализации одинакова: один конфиг retention. Новых опубликованных разрезов B **не даёт** — это снято после N1.

## Правило выбора (согласовано Fable и Astra)
Ответ Oleksandr на вопрос «что нужно от данных раунда после его закрытия»: «снимки заранее выбранных показателей, пересчёт в пределах 90 дней» → A; «пересчёт тех же метрик или офлайн-анализ в течение года после первой кампании» → B. Архитектура и STAGES корректны при любом варианте; зависят только задачи с пометкой [17]: 0.18, 0.19, 1.31, 1.36.
