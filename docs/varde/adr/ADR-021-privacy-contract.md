# ADR-021: Контракт приватности — единый сервис выдачи; граница доверия

Статус: **Accepted** (механизм — раунд 2; граница доверия — решения Oleksandr 12.10 и 13.10: вариант B для всех опросников; часть руководителя — правило (a), решение 13.10). Изменено delta 12.10: спор 21 закрыт — анонимность выбирается перед стартом каждого опросника и защищает от клиента и внешних каналов, а не от трёх админов; вариант A, альтернатива (b) и правило выбора сняты в историю; raw-экспорт с флагом заменён классом `rows` (ADR-025). Дополнено 16.10: куда уходят числа одного клиента (`round_client`); «alle» проверяет ячейки клиентов и ролей вместе (правило 7 release).

## Контекст
На 11.10 порог 3 был реализован только в UI (`dashboard.html::teiknFilter()`); `GET /api/svar` и `csv()` отдают строки целиком; часть руководителя лежит в той же строке, а старый дашборд показывает ответы единственного руководителя в `leiartabell()` — форма прямо говорит, что эти ответы «ikkje anonyme på same måte». Порог k на одной выдаче не защищает от разности двух выдач: (3 «да», 3 «нет») → (4, 3) раскрывает ответ нового респондента. Вопрос «от кого защищаем» модели решить не могли; Oleksandr ответил 12–13.10: трое сотрудников Vardahei IT видят все ответы в обоих режимах (в опроснике по безопасности — с инициалами, в анонимном — без), клиент получает сводку без инициалов и без строк; анонимный режим защищает от клиента и внешних каналов. Это вариант B для всех раундов.

## Принято
- Модуль `privacy` — единственная точка выдачи агрегатов и строк: дашборд, CSV, экспорт, ассистент, отчёты, Atlas. Обход — blocking (lint + тест).
- Класс `aggregate`, `part = common`: порог n ≥ k = 3 на группу; подавление дополнительных групп, восстановимых вычитанием; малые клиенты видны только суммарно — в обоих режимах идентификации (ADR-025). Только этот класс уходит клиенту и во внешние каналы.
- Класс `rows` (ADR-025): строки общей части для трёх админов под AuditLog в обоих режимах — в идентифицированных раундах с `respondent_key`, в анонимных без ключа; включает экспорт для команды и возврат данных клиенту по его требованию (ADR-017); в снимки, клиентский CSV, ассистента, Atlas и отчёт не попадает. Отдельного raw-экспорта с флагом и причиной нет — его роль выполняет `rows`.
- Для `part = leader` — правило (a) ниже; строки leader не входят в снимки по клиенту (`round_client`, `all_clients`), CSV, контекст ассистента, Atlas и автоматический отчёт клиенту; единственная leader-population снимков — `leaders_all` для админ-дашборда (ADR-020).
- Timestamp ответа — день. Прогресс наружу только суммарно; строк по сессиям в API нет.
- Released-снимок неизменяем и создаётся только через `privacy.release()`; внешние каналы (отчёт, Atlas, ассистент, тренды) читают только released.
- Числа одного клиента — ячейки `round_client` (released и живые) и сохранённые Finding клиента — выходят из `privacy` только в его собственный канал (отчёт 5.1, клиентский CSV, handover) и в дашборд админа; собственный канал не получает рядом общих чисел (`all_clients`, суммы по клиентам). Любой другой канал (Atlas, ассистент, тренды, сводки по нескольким клиентам) берёт числа по клиентам только из `all_clients`, где дополнительное подавление между клиентами уже применено. Причина: клиент B, скрытый в `all_clients` рядом с малым клиентом C, виден в своём `round_client`, и C = итог − остальные. Решение Oleksandr 16.10; lint `varde/round-client-exits`, тест `apps/api/test/privacy/subtraction-attack.test.ts`.
- «alle» (`all_clients`) безопасен сам по себе: ячейки клиентов и ролей — маргиналы одной таблицы клиент × роль, и никакая линейная комбинация видимых ячеек не определяет набор групп клиент × роль с 0 < n < k — ни в одной выдаче, ни в живом виде, ни разностью двух выдач для атакующего, который знает, у какого клиента какие роли, но не знает, кто ответил между выдачами; разности — по компонентам связности структуры, при допущении, что между выдачами ответы только прибавляются (`privacy/cross.ts`, правило 7 release). Найденный разрез скрывает ячейку роли, никогда клиента или итог; разность — переносит ячейку разреза, как правило 2. «Før og etter» для всех клиентов раунда скрывает итог, если итог минус отчёт одного скрытого клиента оставляет других скрытых < k. Решения Oleksandr 16.10; тесты `apps/api/test/privacy/subtraction-attack.test.ts`, `cross.test.ts`.

## Часть руководителя (`part = leader`) — правило (a), решение Oleksandr 13.10, одинаково в обоих опросниках
Руководителей у клиента 1–2, порог k невыполним, а респонденту обещано не «анонимно», а «используем, когда садимся с вами». Блок руководителя есть в обоих опросниках (решение 5 от 12.10); связь частей — общий `respondent_key` в идентифицированных раундах и общий `source_id` у импортированных строк — после решения 13.10 допустима для админов (ADR-025), но выдача остаётся раздельной: канал leader с классом `rows` не смешивается, а клиент и внешние каналы связь не получают.
- **Leader вне k.** Отдельный эндпоинт `GET /clients/:id/leader-answers`: только админ-сессия, выдача по одному клиенту, каждое чтение в AuditLog (кто, клиент, когда) в одной транзакции с ответом; эндпоинт никогда не возвращает `part = common`; пометка «ikkje anonymt» в форме руководителя (1.14) и в уведомлении 0.18. Сводные показатели по руководителям всех клиентов — только через `privacy` с population `leaders_all` (ADR-020) и k; ячеек leader по одному клиенту в снимках нет. Правила FUNN по части руководителя и кросс-правило F12×B13 идут тем же каналом (`channel = leader`, ADR-026). Цена: S; паритет 1.27 по руководителям сохраняется.

## Подавление с учётом истории выдач (`privacy.release()`)
Единица — ячейка `(round, population, metric_version, group)` со значениями `(n, numerator)`. Новый release безопасен, если:
1. для каждой ячейки `n ≥ k`;
2. для каждого ранее released снимка той же `(round, population)` таблица разностей `(Δn, Δnumerator)` удовлетворяет тем же правилам: `Δn = 0` или `Δn ≥ k`; ячейки с `0 < Δn < k` не обновляются — в новом снимке повторяется предыдущее released значение (carry-forward) с пометкой `stale`;
3. подавление дополнительных ячеек применяется и к таблице разностей: если `Δ(итог) − Δ(роль A)` даёт восстановимую разность `< k`, carry-forward получает и итог или роль A;
4. набор метрик раунда фиксируется при первом release; новые метрики применяются только к раундам, у которых ещё нет release (выданное нельзя «развыдать»);
5. ручной release — только через ту же функцию, обхода нет; запись в AuditLog;
6. ячейки прогресса «обрыв по вопросу» и «активные сессии» подчиняются правилам 1–3; точный счётчик ответов на RoundClient (для отклика) — принятое исключение: он раскрывает факт участия, не ответ, и назван в уведомлении респондентам.

Отрицательные тесты (0.15b, повтор на реальных эндпоинтах в 1.32): `(3,3) → (4,3)` → ячейка carry-forward; итог +4 при роли A +3 и роли B +1 → роль B и одна из {итог, роль A} carry-forward; ручной release после одного нового ответа → ни одна ячейка ответов не меняется; обрыв по вопросу 2 → 3 → carry-forward до Δn ≥ k; добавление метрики к раунду с release → отклонено.
