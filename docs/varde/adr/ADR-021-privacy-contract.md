# ADR-021: Контракт приватности — единый сервис выдачи; граница доверия

Статус: механизм Accepted. Граница доверия: для идентифицированных раундов (опросник по безопасности) — **вариант B, решено Oleksandr 12.10** (ADR-025); для анонимных раундов (KI-опросник) — **Proposed, спор 21 открыт [O3]**, правило выбора ниже. Правило для части руководителя добавлено после проверки одобрения и ждёт подтверждения Oleksandr [O4]. Изменено delta 12.10: область спора 21 сужена до анонимных раундов; добавлен раздел «Идентифицированные раунды»; raw-экспорт варианта B нужен только анонимным раундам.

## Контекст
На 11.10 порог 3 был реализован только в UI (`dashboard.html::teiknFilter()`); `GET /api/svar` и `csv()` отдают строки целиком; часть руководителя лежит в той же строке, а старый дашборд показывает ответы единственного руководителя в `leiartabell()` — форма прямо говорит, что эти ответы «ikkje anonyme på same måte». Порог k на одной выдаче не защищает от разности двух выдач: (3 «да», 3 «нет») → (4, 3) раскрывает ответ нового респондента. Вопрос «от кого защищаем» модели решить не могут. 12.10 опросник по безопасности стал идентифицированным (инициалы, вид по сотруднику, ADR-025), и для него Oleksandr решил: трое сотрудников Vardahei IT видят ответы по человеку, клиент получает сводку без инициалов — это вариант B. KI-опросник остался анонимным, и для него вопрос «от кого защищаем» по-прежнему открыт.

## Принято (обе стороны)
- Модуль `privacy` — единственная точка выдачи агрегатов и разбивок: дашборд, CSV, ассистент, отчёты, Atlas. Обход — blocking (lint + тест).
- Для `part = common`: порог n ≥ k = 3 на группу; подавление дополнительных групп, восстановимых вычитанием; малые клиенты видны только суммарно — в обоих режимах идентификации (ADR-025).
- Для `part = leader` — отдельное правило ниже; строки leader не входят в снимки по клиенту (`round_client`, `all_clients`), CSV, контекст ассистента, Atlas и автоматический отчёт клиенту; единственная leader-population снимков — `leaders_all` для админ-дашборда (ADR-020).
- Идентифицированные раунды (delta 12.10, ADR-025): дополнительно класс выдачи `person` — строки по человеку для трёх админов под AuditLog, включая экспорт Master_Analyse для команды; в снимки, клиентский CSV (`aggregate`), ассистента, Atlas и отчёт он не попадает. Режим `privacy` выбирается по `Round.identification`; один модуль, две таблицы отрицательных тестов.
- Timestamp ответа — день. Прогресс наружу только суммарно; строк по сессиям в API нет.
- Released-снимок неизменяем и создаётся только через `privacy.release()`.

## Часть руководителя (`part = leader`) — одинаково в A и B и в обоих опросниках [O4]
Руководителей у клиента 1–2, порог k невыполним, а респонденту обещано не «анонимно», а «используем, когда садимся с вами». Блок руководителя есть в обоих опросниках (решение 5 от 12.10); в идентифицированном опроснике leader Response несёт тот же `respondent_key`, что и общая часть того же человека (нужно для удаления по запросу, ADR-017), но общего submission-ключа нет, и канал leader с каналом `person` не смешивается (ADR-006, ADR-025) — правило ниже одно для обоих.
- **Рекомендовано (a): leader вне k.** Отдельный эндпоинт `GET /clients/:id/leader-answers`: только админ-сессия (и в A — это не анонимные данные, обещание другое), выдача по одному клиенту, каждое чтение в AuditLog (кто, клиент, когда) в одной транзакции с ответом; эндпоинт никогда не возвращает `part = common`; пометка «ikkje anonymt» в форме руководителя (1.14) и в уведомлении 0.18. Сводные показатели по руководителям всех клиентов — только через `privacy` с population `leaders_all` (ADR-020) и k; ячеек leader по одному клиенту в снимках нет. Цена: S; паритет 1.27 по руководителям сохраняется.
- Альтернатива (b): leader под тем же k → раздел пуст у всех шести клиентов, паритет 1.27 по руководителям снимается, ценность для встречи теряется. Цена: минус функция.
- [O4] Oleksandr подтверждает (a): это формулировка обещания респондентам. Правила FUNN по части руководителя и кросс-правило F12×B13 идут тем же каналом (`channel = leader`, ADR-026); при (b) выпадают вместе с разделом.

## Подавление с учётом истории выдач (`privacy.release()`)
Единица — ячейка `(round, population, metric_version, group)` со значениями `(n, numerator)`. Новый release безопасен, если:
1. для каждой ячейки `n ≥ k`;
2. для каждого ранее released снимка той же `(round, population)` таблица разностей `(Δn, Δnumerator)` удовлетворяет тем же правилам: `Δn = 0` или `Δn ≥ k`; ячейки с `0 < Δn < k` не обновляются — в новом снимке повторяется предыдущее released значение (carry-forward) с пометкой `stale`;
3. подавление дополнительных ячеек применяется и к таблице разностей: если `Δ(итог) − Δ(роль A)` даёт восстановимую разность `< k`, carry-forward получает и итог или роль A;
4. набор метрик раунда фиксируется при первом release; новые метрики применяются только к раундам, у которых ещё нет release (выданное нельзя «развыдать»);
5. ручной release — только через ту же функцию, обхода нет; запись в AuditLog;
6. ячейки прогресса «обрыв по вопросу» и «активные сессии» подчиняются правилам 1–3; точный счётчик ответов на RoundClient (для отклика) — принятое исключение: он раскрывает факт участия, не ответ, и назван в уведомлении респондентам.

Отрицательные тесты (0.15b, повтор на реальных эндпоинтах в 1.32): `(3,3) → (4,3)` → ячейка carry-forward; итог +4 при роли A +3 и роли B +1 → роль B и одна из {итог, роль A} carry-forward; ручной release после одного нового ответа → ни одна ячейка ответов не меняется; обрыв по вопросу 2 → 3 → carry-forward до Δn ≥ k; добавление метрики к раунду с release → отклонено.

## Идентифицированные раунды: вариант B (решено 12.10)
Трое админов доверены под AuditLog; живые агрегаты common с порогом k в открытом раунде; released-снимки через `privacy.release()` для отчётов, Atlas, ассистента; leader-эндпоинт по правилу выше; класс `person` (ADR-025) — строки по человеку, только админ-сессия, каждое чтение в AuditLog; raw-экспорт как отдельное исключение не нужен — его роль выполняет `person`. Отрицательные тесты — в ADR-025 и 1.32. Это решение не зависит от ответа по анонимным раундам: при 21A для KI-опросника `privacy` работает в двух режимах по `Round.identification`, предусловие A о единственном держателе credentials относится ко всему инстансу и выполнимо при обоих режимах.

## Вариант A для анонимных раундов: админы внутри модели угроз [O3]

| Что | Определение |
| --- | --- |
| Доверенные субъекты | Только роль «оператор базы» (один человек, по умолчанию Oleksandr), доступ out-of-band: SSH + `varde_backup`/`psql`. Предусловие: SSH/root на VPS и env-файл с credentials `varde_app` — у одного человека; список держателей фиксируется в evidence 0.5/0.8. Журнал подключений: login event trigger (PostgreSQL 17) в базе `varde`; `pgaudit` — только по согласованию с владельцем Atlas, инстанс общий. Это не канал продукта. Админ-UI не доверен никому для `part = common` |
| Разрешённые каналы | Released-снимки через `privacy.release()` с историей выдач: при закрытии раунда и по суточному расписанию в открытом раунде; точный счётчик ответов на RoundClient; прочие агрегаты прогресса под правилами 1–3; leader-эндпоинт по правилу выше; CSV, ассистент, Atlas — только из released |
| Запрещено | Живые распределения common; raw-экспорт; API на уровне строк common; выдержки свободного текста (их читает оператор out-of-band и вносит вручную) |
| Отрицательные тесты | Любой HTTP-эндпоинт, кроме leader-эндпоинта, не возвращает поля `answers`; leader-эндпоинт без админ-сессии → 401, без записи AuditLog невозможен, не возвращает `part = common`; тесты истории выдач выше; endpoint raw-экспорта отсутствует (404); дашборд в открытом раунде показывает `released_at` и пометки `stale` |
| Цена | M: суточные снимки с carry-forward (малые клиенты обновляются редко), меньше обратной связи в кампании, выдержки вручную из psql; обещание: «сотрудники Vardahei через приложение не видят отдельных ответов сотрудников; ответы руководителя не анонимны; один оператор имеет технический доступ под журналом» |

## Правило выбора для анонимных раундов [O3] (согласовано Fable и Astra; область сужена delta 12.10)
Ответ Oleksandr на вопрос «кто не должен иметь возможности восстановить отдельный ответ сотрудника в анонимном KI-опроснике»: «руководитель клиента и внешние» → B; «и трое админов» → A; «и оператор базы» → ни A, ни B не достаточны — нужна отдельная архитектура (например, шифрование на уровне полей с ключом вне досягаемости оператора или другая модель размещения), отдельное решение без предварительного выбора A. Зависят задачи с пометкой [21] в части анонимных раундов: 0.5, 0.8 (предусловие A о единственном держателе), 0.15, 0.15b, 0.18, 1.20, 1.26, 1.27, 1.30, 1.32; идентифицированные раунды идут по варианту B при любом ответе. Правило для leader и задача 1.14 от варианта A/B не зависят, но при выборе (b) [O4] из 1.27 и 1.32 выпадают leader-части; структура этапов одинакова.
