# ADR-024: Доказуемый импорт и переключение с kartlegging

Статус: Accepted (новое решение Astra принято; дополнено в раунде 2 по B9, B10, B13). Изменено delta 12.10: раунд 1 (Forms) импортируется как идентифицированный раунд с Response, а не как снимки; `F1` → `respondent_key`; срок архива `svar.jsonl` — только «после отчёта, не позднее 90 дней после cutover»; итерация 3 — `source_id` = постоянный `id` строки `svar.jsonl` (для раунда 1 — ключ записи), а не hash содержимого: identity переживает очистку при rollback; итерация 4 — подавление по частям при любом импорте и таблица путей возврата удалённого; итерация 5 — identity обеих частей из постоянного `id` строки (`source_id = id`, уникальность по `(source_id, part)`; тройка по `content_hash` снята — она склеивала разные отправки), replay Submission API после удаления сверяется с журналом; итерация 6 — после rollback kartlegging работает только на чтение, приём заново не открывается (решение оркестратора 13.10, Oleksandr может отменить).

## Контекст
На 11.10 `kartlegging/private/runde1.js` содержал только агрегаты Forms; с 12.10 он содержит 57 ответов раунда 1 по людям с инициалами, без свободного текста и без части руководителя (формат — `tools/runde1_fra_excel.py`), и дашборд сравнивает раунды по фирмам, вопросам и людям. Строка `svar.jsonl` содержит и общую часть, и часть руководителя (`leiardel`) вместе, а в опроснике по безопасности — инициалы в `svar.F1`; старый сервер доверяет присланной строке `versjon`.

## Импорт
- `ImportManifest`: источник, hash файла, число строк, принятых, отклонённых с причинами, статус, кто запустил, итоговая сверка.
- Строка `svar.jsonl` → common Response с `source_id = id` строки — UUID, который kartlegging присваивает при приёме (`docs/kartlegging-teknisk.md`, `server.js::randomUUID`); identity строки не зависит от её содержимого и потому переживает очистку части руководителя при rollback; hash строки и файла — только контроль целостности в ImportManifest; строка без `id` или с повторяющимся `id` → rejected с причиной (изменено delta 12.10, итерация 3: раньше `source_id = hash(строки)`). Для опросника по безопасности `svar.F1` нормализуется в `respondent_key` и в `answers` не попадает (ADR-025), `versjon` строки сопоставляется с TemplateVersion по дате; если `leiardel = true` — дополнительно leader Response с **тем же `source_id = id` строки** (изменено delta 12.10, итерация 5: после решения 13.10 связь частей от админов не скрывается, ADR-025) и, в опроснике по безопасности, с тем же `respondent_key`; уникальный индекс по `(source_id, part)`; FK между частями нет; обе создаются в одной транзакции; у каждой части свой `submission_id` и `content_hash` (ADR-006). **Решение о каждой части принимается отдельно, при любом импорте, и зависит только от журнала удалений (`DeletionLedger`, ADR-017) и ключа части `(source_id, part)` — не от того, что есть в базе у другой части** (итерация 4). Часть `existing`, если Response с таким `(source_id, part)` уже есть; `suppressed`, если в журнале есть tombstone с таким `(source_id, part)`; иначе `accepted`. Следствия: удалённая часть руководителя не возвращается ни при повторном импорте, ни при импорте после restore дампа, снятого до импорта; удалённая common-часть не тянет за собой неудалённую leader-часть; очищенная при rollback строка (`leiardel = false`, `id` прежний) даёт common `existing` и ничего по leader; две разные строки с одинаковой частью руководителя — две leader Response при любом разбиении импорта на проходы, потому что ключ — `id` строки, а не содержимое.
- Сверка по счётчикам отдельно, по частям: строк источника = common `accepted` + `rejected` + `existing` + `suppressed`; строк с `leiardel = true` = leader `accepted` + `rejected` + `existing` + `suppressed`, где отклонённая строка (нет `id`, дубль `id`, не проходит валидацию) считается `rejected` в common-счётчике и — только если у неё `leiardel = true` — в leader-счётчике, и ни одной части не создаёт; расхождение → manifest `failed`, транзакция откатывается.
- Связь частей импортированной строки хранится как общий `source_id` (допустимо для админов по решению 13.10; клиенту и внешним каналам не выдаётся — ADR-021, ADR-025). Живые отправки связи не хранят: она им не нужна (ADR-006). После удаления архива (`svar.jsonl` и `runde1.js`, задача 1.36) исходные строки восстановить нельзя.
- TemplateVersion для импорта восстанавливается из `sporsmal.js` соответствующей версии (git-история kartlegging или «текст на дату экспорта» с пометкой в manifest).
- Раунд 1 (Forms, `runde1.js`) → Round типа `external_import` с `identification = initials` на восстановленной TemplateVersion опросника по безопасности (те же id вопросов F2–F19 и вариантов — сопоставление `SP`/`SVAR` из `runde1_fra_excel.py`; F15 как multi; F1 → identifier; F20–F22 без ответов): каждая запись → common Response с `source_id = sha256("runde1|" + k + "|" + init)` — ключ записи, по которому `runde1_fra_excel.py` её и собирает (`folk[(k, ini)]`; запись при очистке только удаляется целиком, поэтому ключ стабилен) и `respondent_key` из `init`; записи, чей `source_id` есть в журнале удалений, пропускаются как `suppressed`, уже импортированные — `existing`; leader Response нет (Forms не имел части руководителя); ImportManifest с hash `runde1.js` как контролем целостности. Сверка: записей источника = `accepted` + `existing` + `suppressed`, leader = 0; counts по клиентам, snittscore, kritisk andel и `persons_per_zone` раунда 1 равны расчёту старого дашборда на источнике без записей из журнала (при пустом журнале — старому дашборду как есть; fixture-процедура паритета вычитает записи журнала и перечисляет их в evidence числом); повторный импорт — 0 новых строк. Метрики `comparable` с пояснением (ADR-020). Fixtures для тестов — синтетические (выдуманные инициалы, тот же формат); сверка с настоящим файлом — только числами в evidence, без инициалов. Снимки раунда 1 создаются тем же `privacy.release()`.
- Паритет проверяется на согласованных fixtures с перечнем намеренных исправлений.

## Репетиция (1.34)
В staging: свежий импорт, сверка, DNS-план, rollback выполнен один раз, отчёт; после rollback kartlegging только на чтение — повтор старого POST → 410, `svar.jsonl` без новых строк. Полный цикл идентичности (итерация 3): удаление по запросу трёх видов (`respondent` в идентифицированном раунде, только leader-часть и только common-часть в анонимном раунде) → rollback с очисткой архива по журналу → повторный cutover с повторным импортом: 0 новых строк, вырезанная часть руководителя не воссоздана, удалённые строки `suppressed`, остальные `existing`, счётчики сходятся, снимки не меняются.

## Production cutover (1.35)
1. Oleksandr закрывает текущую кампанию в kartlegging (все RoundClient «stengd»); запись в `hendingar.jsonl`.
2. Финальный импорт `svar.jsonl` с manifest; сверка счётчиков (с `suppressed`) и counts по клиентам против старого дашборда за вычетом записей журнала удалений.
3. Go/no-go: чек-лист (сверка, тесты инвариантов 1a–1c зелёные на artifact hash, бэкап снят) с подписью Oleksandr в `stages/stage-1/cutover.md`.
4. DNS `kartlegging.vardahei.tech` → Varde. В той же процедуре `svar.jsonl` и `private/runde1.js` выносятся из старого приложения в зашифрованный архив (age, ключ оператора, вне VPS); kartlegging остаётся только как redirect, не хранит raw и не отдаёт `/runde1.js` (изменено delta 12.10: `runde1.js` — тоже raw с инициалами).
5. Rollback (до 7 дней): DNS назад; оператор восстанавливает оба файла архива в kartlegging (действие в AuditLog Varde) и применяет журнал удалений (список выдаёт Varde; изменено delta 12.10): из `svar.jsonl` удаляются строки, чей `id` есть в журнале как `source_id`, из `runde1.js` — записи, чей ключ `(k, init)` даёт `source_id` из журнала как tombstone common-части (строка или запись целиком, вместе с частью руководителя); у строк `svar.jsonl`, чей `id` есть в журнале только как tombstone leader-части, часть руководителя вырезается (`leiardel = false`, B-ответы удалены), а `id` строки не меняется — повторный импорт узнаёт её как `existing`. **После rollback kartlegging работает только на чтение** (изменено delta 12.10, итерация 6): раунды остаются «stengd» с шага 1, приём не открывается — `/api/svar` и `/api/framdrift` отвечают 410, runner показывает «avslutta», дашборд и админка только показывают восстановленный и очищенный архив; `svar.jsonl` после очистки не меняется, поэтому старый код `valider()` не присваивает новых UUID повторённым старым POST, и удалённому нечем вернуться. Если в окне rollback нужно собирать ответы — это новый раунд в Varde, не переоткрытие старого приёма. Ответы, принятые Varde после переключения и в окне rollback, остаются в базе Varde и помечаются `accepted_during_cutover`; при повторном cutover архивируется тот же очищенный `svar.jsonl`, повторный импорт применяет журнал сам, `accepted_during_cutover` не импортируются заново и не теряются.
6. Архив удаляется после отчёта клиентам, но не позднее 90 дней после cutover независимо от готовности отчёта (задача 1.36); raw в Varde хранится бессрочно (ADR-017), поэтому третьего срока нет.

## Пути возврата удалённого и их подавление (итерации 4–6)
Два инварианта. Первый: подавление зависит только от журнала удалений и ключей — `(source_id, part)` для импортированных частей (`source_id` = `id` строки `svar.jsonl` или ключ записи раунда 1) и `submission_id` для живых отправок, — а не от содержимого базы, поэтому порядок restore, импорта и rollback не важен. Второй: после cutover в `svar.jsonl` и `runde1.js` ничего не дописывается — kartlegging после rollback только на чтение, поэтому старый код не может выдать удалённому ответу новый `id`. Все пути, которыми удалённое по запросу могло бы вернуться:

| --- | --- | --- | --- | --- |

| Последовательный импорт (A, затем A+B) при одинаковой части руководителя у разных строк | A `existing`, B `accepted` | A `existing`, B `accepted` — две leader Response, ключ не зависит от содержимого | аналогично | 1.8 |

## Альтернативы
Ручной перенос; раунд 1 только как снимки без Response (план 11.10; снято delta 12.10: сравнение по людям и экспорт для шефа требуют строк); leader-часть без `source_id` и без общего ключа с common (план 11.10 ради анонимности от админов; снято решением 13.10 — без ключа leader нельзя ни идемпотентно импортировать, ни подавить по журналу); `source_id = hash(строки)` (редакция до итерации 3: очистка части руководителя при rollback меняет hash → дубль или срыв сверки при повторном импорте); identity leader-части по тройке `(round, client, content_hash)` (итерация 4; снято: склеивает разные отправки с одинаковой частью руководителя, результат зависит от разбиения на проходы); откладывать удаление до закрытия окна rollback (отклонено: право на удаление исполняется сразу, а окон rollback может быть несколько).

## Последствия
Тесты: «повторный импорт без дублей (common и leader)», «counts совпадают по счётчикам, включая `existing` и `suppressed`», «строка из журнала удалений при импорте не восстанавливается», «полный цикл удаление → rollback с очисткой → повторный cutover: 0 новых строк, вырезанная часть не воссоздана», «строка без `id` → rejected», «дамп до импорта → импорт → удаление только leader-части анонимного раунда → restore + журнал → повторный импорт: common создана, leader `suppressed` по `(source_id, leader)`», «импорт A, затем A+B с одинаковой частью руководителя → две leader Response», «удалённая common не блокирует неудалённую leader при импорте», «rejected строка с `leiardel = true` учтена в обоих счётчиках, без `leiardel` — только в common, частей не создано», «replay POST после forget → без вставки», «после rollback POST в kartlegging → 410, `svar.jsonl` без новых строк, повторный cutover → 0 новых строк», «импорт неочищенного архива после rollback → удалённое `suppressed`», «rollback не теряет ответы Varde и не возвращает удалённое», «удалённая часть руководителя анонимного раунда после rollback вырезана из своей строки», «удалённая запись раунда 1 после rollback отсутствует в `runde1.js`». Цена: checkpoints 1a и 1c.
