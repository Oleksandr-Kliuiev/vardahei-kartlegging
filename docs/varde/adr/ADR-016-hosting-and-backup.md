# ADR-016: Размещение на общем VPS — измерить до решения; бэкап шифрованный и восстанавливаемый отдельно

Статус: Accepted (дополнение Astra принято). Изменено delta 12.10: журнал удалений экспортируется отдельно и применяется при restore. 13.10 (решения Oleksandr): заместители для восстановления — Asbjørn и Bjarte, держатели приватного ключа age вместе с Oleksandr; целевых RPO/RTO нет (условие снято с ворот G3); restore-drill отложен, остаточный риск записан ниже; действия на хостинге выполняет хостинг-оператор (Claude; в `docs/BESLUTNINGER.md` — «Claude-оркестратор»), кодер доступа к VPS и секретам не получает; ключи age без пароля на зашифрованном диске держателя; изоляция `varde` — три строки pg_hba.

**Изменено 13.10 (решение Oleksandr):** бэкап, ключи age и uptime-monitor пока отложены; до их включения данные Varde существуют только на VPS — принятый остаточный риск.

## Контекст
Тот же VPS, Docker, общий Caddy, своя база в общем Postgres 17. Вопрос «хватит ли 8 ГБ на 14 контейнеров» без измерений не имеет ответа. Изменено delta 12.10: на 12.10 на VPS 17 контейнеров, в том числе стек Supabase `dnd-*`; свободно около 5,3 из 7,9 GB RAM, swap нет — вход для 0.12; решение не меняется. Копия `pg_dump` в SharePoint без шифрования — не бэкап. Atlas — внутренняя платформа Vardahei (13.10): отдельного владельца и согласования нет, superuser-шаги на общем инстансе выполняет хостинг-оператор.

## Решение
- База `varde`, роли `varde_app` и `varde_backup` (read-only); независимые credentials; роль Atlas не имеет доступа к `varde` (проверяется тестом подключения). Изоляция по факту (пакет этапа 0, решение 13.10 «Изоляция базы `varde`»): три строки в `pg_hba.conf` перед общими `host`-строками — `host varde varde_app,varde_backup all scram-sha-256`, `host all varde_app,varde_backup all reject`, `host varde all all reject` — одна процедура независимо от того, superuser ли роль приложения Atlas (хостинг-оператор проверяет `rolsuper` только для записи риска; REVOKE/GRANT CONNECT на базах Atlas не делается; `varde` закрыта от PUBLIC в `varde-roles.sql`); local socket внутри `atlas-db-1` остаётся единственным каналом superuser-обслуживания (`docker exec … psql` без `-h`), через который идут все superuser-шаги к `varde`; остаточные риски записаны: superuser может переписать `pg_hba.conf` и обойти журнал подключений (держатели superuser — Vardahei, поимённо в ADR-021 и evidence), а любая superuser-сессия инстанса, открытая в другой базе (приложение Atlas, если его роль superuser; держатели пароля `$POSTGRES_USER`), технически имеет полный доступ к `varde` независимо от pg_hba (ADR-021; пересмотр до cutover 1.35).
- Этап 0 (задача 0.12): неделя метрик (RAM, swap, CPU, disk latency, Postgres connections, пики) и baseline p95 эталонного эндпоинта Atlas. Стенд: stub-эндпоинт отправки с той же транзакцией записи JSONB в `varde`, синтетическая pg-boss-задача (держит соединение и ждёт mock-HTTP 20 с — модель AI-вызова), бэкап — одновременно с 100 виртуальными телефонами. Пороги go: без OOM; ≥25 % RAM в запасе под пиком; p95 отправки < 1 с; p95 Atlas ≤ 2× baseline и 0 ошибок 5xx. Тот же тест повторяется против настоящего Submission API перед cutover (задача 1.33; там же модуль stub удаляется). При провале сначала выносятся необязательные workloads; Varde переносится отдельно, если запас недостаточен или нужна независимая доступность.
- Бэкап: ночной `pg_dump` → шифрование `age` на три recipient (приватные ключи у Oleksandr, Asbjørn и Bjarte — решение 13.10; каждый генерирует свою пару на своём устройстве, без пароля, на зашифрованном диске — решение 13.10 «Ключи age без пароля»; на VPS только публичные ключи в `/etc/varde/recipients.txt`) → `rclone` в отдельный сайт SharePoint `VardeBackup` (app-only доступ с client secret — сертификат OneDrive-backend rclone не поддерживает; `Sites.Selected` только на этот сайт); рядом с дампом — `meta.json` (sha образа, последняя миграция, владелец event trigger — superuser источника, роль с этим именем `restore.sh` создаёт на чистой машине до `pg_restore`), canary-файл для проверки ключей, tar образов api и backup и kit скриптов восстановления с конфигами; копии старше 35 дней удаляет сама ротация в `backup.sh` (именованные файлы, не версии одного файла — версионирование библиотеки к ним не применяется); корзина SharePoint может держать удалённое ещё до 93 дней, purge корзины ничем не подтверждается, поэтому реестр 0.19 и ADR-017 записывают эффективный максимум 35 + 93 = 128 дней при работающем ночном бэкапе (ротация идёт после успешного дампа; при сбое бэкапа — до восстановления по оповещению heartbeat плюс 128); экспорты журнала в `ledger/` не ротируются (DeletionLedger — бессрочно). Restore-скрипт и runbook для заместителей на нюношке (PRINCIPLES §19): restore = дамп + применение последнего экспорта журнала удалений; скрипт печатает возраст копии и затраченное время только для сведения — целевых RPO/RTO нет (решение 13.10), checkpoint 0b и приёмка 0.10 от них не зависят; 0.10b (WAL-архивирование или частые дампы) не планируется. Escrow прод-секретов не делается (решение 13.10): при восстановлении на новой площадке секреты генерируются заново, новый client secret Entra выпускает админ тенанта; заместителям — только свой ключ age и runbook. Изменено delta 12.10: журнал удалений (`DeletionLedger`, ADR-017) экспортируется отдельным age-файлом в тот же SharePoint-поток сразу после каждой записи; restore-скрипт = дамп + применение последнего экспорта журнала (журнал из старого дампа не используется, при расхождении берётся объединение), поэтому дамп, снятый до запроса, не возвращает удалённое; после восстановления автоматически повторяется удаление просроченных данных.
- **Остаточный риск (принят Oleksandr 13.10): бэкап не проверен восстановлением человеком на чистой машине.** Restore-drill на чистой машине без исходного VPS и ежеквартальный drill (5.3) отложены; `restore.sh` проверяется только автоматически — roundtrip в CI (настоящий `backup.sh` → настоящий `restore.sh` в чистый кластер Postgres с проверкой владельцев, роли-владельца event trigger, самого триггера, журнала и `/health`). Ошибка в runbook, в доступе заместителей к библиотеке, в tar образов или в расшифровке реальным ключом обнаружится только при настоящем восстановлении. Остающиеся защиты: roundtrip на каждом коммите, проверка ключей canary-файлом, heartbeat ночного бэкапа, листинг библиотеки и `meta.json` в evidence. Пересмотр — перед этапом 3 (live poll требует восстановления в минутах) или раньше по решению Oleksandr.
- Внешняя проверка доступности (uptime-monitor вне VPS) с оповещением; тот же сервис держит heartbeat ночного бэкапа (пакет этапа 0: `backup.sh` шлёт ping после успешной загрузки, пропуск → оповещение), иначе сбой бэкапа никто не заметит.
- Действия на хостинге (VPS, superuser-шаги на `atlas-db-1` через `docker exec … psql` внутри контейнера без чтения env Atlas, Caddy, сети Docker, cron бэкапа, деплой, uptime-monitor) выполняет хостинг-оператор (Claude; в `docs/BESLUTNINGER.md` — «Claude-оркестратор») по runbook-шагам пакета этапа с проверкой и откатом; кодер работает только в репо, CI и локально; оркестратор (Sol) на VPS не ходит. За Oleksandr — регистрации в Entra и доступ к SharePoint (админ тенанта), DNS-запись, своя пара age (решение 13.10); выпущенные им client secrets он вписывает в env на VPS сам — уточнение пакета этапа 0 к решению 3, чтобы секрет не проходил через чат хостинг-оператора (`stages/stage-0.md` §9 п. 14; Oleksandr может отменить).

## Альтернативы
Свой Postgres-контейнер (ещё память); отдельный VPS (цена и вторая площадка — только по результату измерений); `--onedrive-hard-delete` в rclone (минуя корзину — максимум 35 дней). Это флаг клиента, а не свойство гранта: root на VPS читает `backup.env` и может вызвать безвозвратное удаление сам, если грант `Sites.Selected write` допускает `permanentDelete`, — тогда копии не защищены от root в обоих вариантах и развилка сводится к сроку хранения; если не допускает, флаг неисполним. Хостинг-оператор проверяет это на тестовом файле в 0.10, решение Oleksandr — после проверки, по умолчанию не включено (`stages/stage-0.md` §9 п. 6); свой uploader вместо rclone (сертификат вместо client secret) — не планируется.

## Последствия
Ответ на вопрос Astra №3 (допустимые простой и потеря данных, кто восстанавливает): восстанавливают Oleksandr или заместители по runbook; целевых RPO/RTO нет (решение 13.10): при ночном дампе фактическая потеря — до суток, при сбое бэкапа — больше, до восстановления по оповещению heartbeat; простой не нормирован; бэкап до первого настоящего восстановления остаётся непроверенным человеком — риск принят. Цена: M.
