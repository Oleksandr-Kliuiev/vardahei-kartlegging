# ADR-016: Размещение на общем VPS — измерить до решения; бэкап шифрованный и восстанавливаемый отдельно

Статус: Accepted (дополнение Astra принято)

## Контекст
Тот же VPS, Docker, общий Caddy, своя база в общем Postgres 17. Вопрос «хватит ли 8 ГБ на 14 контейнеров» без измерений не имеет ответа. Изменено delta 12.10: на 12.10 на VPS 17 контейнеров, в том числе стек Supabase `dnd-*`; свободно около 5,3 из 7,9 GB RAM, swap нет — вход для 0.12; решение не меняется. Копия `pg_dump` в SharePoint без шифрования и версионирования — не бэкап.

## Решение
- База `varde`, роли `varde_app` и `varde_backup` (read-only); независимые credentials; роль Atlas не имеет доступа к `varde` (проверяется тестом подключения).
- Этап 0 (задача 0.12): неделя метрик (RAM, swap, CPU, disk latency, Postgres connections, пики) и baseline p95 эталонного эндпоинта Atlas. Стенд: stub-эндпоинт отправки с той же транзакцией записи JSONB в `varde`, синтетическая pg-boss-задача (держит соединение и ждёт mock-HTTP 20 с — модель AI-вызова), бэкап — одновременно с 100 виртуальными телефонами. Пороги go: без OOM; ≥25 % RAM в запасе под пиком; p95 отправки < 1 с; p95 Atlas ≤ 2× baseline и 0 ошибок 5xx. Тот же тест повторяется против настоящего Submission API перед cutover (задача 1.33). При провале сначала выносятся необязательные workloads; Varde переносится отдельно, если запас недостаточен или нужна независимая доступность.
- Бэкап: ночной `pg_dump` → шифрование `age` (приватный ключ у Oleksandr и у заместителя, не на VPS) → `rclone` в SharePoint Vardahei; версии хранятся 35 дней (ADR-017); корзина SharePoint может держать удалённое ещё до 93 дней, поэтому в задаче 0.10 проверяется фактическое исчезновение (политика purge корзины для библиотеки бэкапов, подтверждено в drill) либо реестр 0.19 записывает эффективный максимум +128 дней. Целевые RPO/RTO и заместитель — вход от Oleksandr (ворота G3); restore-drill на чистой машине без исходного VPS измеряет фактические RPO (возраст копии) и RTO (время до рабочего сервиса). Checkpoint 0b не принимается, пока измеренные RPO и RTO не ≤ целей: если ночного дампа недостаточно, в 0.10b реализуется WAL-архивирование (или более частые дампы) и drill повторяется до успеха. Drill повторяется ежеквартально; после восстановления автоматически повторяется удаление просроченных данных.
- Внешняя проверка доступности (uptime-monitor вне VPS) с оповещением.

## Альтернативы
Свой Postgres-контейнер (ещё память); отдельный VPS (цена и вторая площадка — только по результату измерений).

## Последствия
Ответ на вопрос Astra №3 (допустимые простой и потеря данных, кто восстанавливает) определяет, достаточно ли ночного дампа. Цена: M.
