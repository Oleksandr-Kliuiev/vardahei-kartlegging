# ADR-006: Раннер — контракт черновика и надёжной отправки (решения 6 и 23)

Статус: Accepted (дополнение Astra принято). Изменено delta 12.10: identifier-вопрос нормализуется в `respondent_key`; требование «у частей нет общего ключа» снято решением 13.10 (связь допустима для админов, ADR-025) — живые отправки связи по-прежнему не хранят, импортированные несут общий `source_id` (ADR-024); Submission API сверяет `submission_id` с журналом удалений.

## Контекст
Runner должен переживать плохой интернет. Сейчас `server.js::/api/svar` на каждый POST создаёт новый UUID, а `valider()` проверяет допустимость значений, но не путь показа; повтор запроса после потери HTTP-ответа создаёт дубль.

## Решение
Черновик:
- Ключ в localStorage = `varde:<round_client_code_hash>:<template_version>`; TTL = срок RoundClient; удаляется после подтверждённой отправки; черновик другой версии игнорируется.
- Обещание: восстановление после перезагрузки страницы и обрыва связи, пока браузер хранит данные. Полный offline (service worker, отправка позже) в этап 1 не входит.

Отправка:
- Общая часть и часть руководителя — две независимые отправки. Клиент генерирует два случайных `submission_id` (по одному на часть) при старте черновика и хранит оба в черновике; отдельного ключа связи между живыми отправками нет: в идентифицированных раундах обе части несут один `respondent_key` (ADR-025) — это и есть связь, допустимая для админов; в анонимных раундах части не связаны, и связь не нужна; импортированные строки связаны общим `source_id` (ADR-024). Изменено delta 12.10: раньше отсутствие ключа было требованием анонимности от админов, после решения 13.10 — только отсутствием потребности.
- Сервер: уникальный индекс по `submission_id` и сохранённый `content_hash`. Повторный POST с тем же id и тем же hash возвращает тот же результат (201 + тот же ответ) и не создаёт строки; тот же id с другим содержимым → 409. Изменено delta 12.10: та же сверка выполняется и по журналу удалений (`DeletionLedger`, ADR-017) — если `submission_id` есть в журнале как tombstone, unique index его уже не держит, поэтому tombstone с тем же `content_hash` даёт тот же идемпотентный ответ без вставки, с другим — 409; удалённый ответ через replay не возвращается. Квота RoundClient расходуется при вставке строки, не при запросе, поэтому replay её не тратит. Транзакция «проверить (строка, журнал) → записать → ответить».
- Сервер повторно вычисляет путь показа по `rules/runner`: ответы на невидимые вопросы отбрасываются, `exclusive_options` и `choices_from` проверяются, `template_version` берётся из RoundClient, а не из тела запроса.
- `submission_id` не связан с Contact, Registration или ProgressEvent.
- Изменено delta 12.10 (ADR-025): в раундах с `identification = initials` сервер нормализует ответ на identifier-вопрос (trim, верхний регистр, ≤ 8 символов) в `Response.respondent_key` общей части и удаляет его из `answers`; в анонимных раундах присланный identifier → 400. В идентифицированном раунде leader-отправка несёт тот же `respondent_key` (клиент берёт его из черновика; без него → 400): это атрибут человека для удаления по запросу (ADR-017); FK между частями нет.

## Альтернативы
Серверный UUID (дубли при повторе); персональные токены (конец анонимности, решение 9).

## Последствия
Тесты: «повторный POST создаёт одну запись и не тратит квоту», «тот же id с другим содержимым → 409», «потеря ответа после commit → повтор возвращает успех», «ответ на невидимый вопрос отбрасывается», «replay после forget: тот же hash → ответ без вставки, другой → 409», «между частями нет FK». Общая ссылка по-прежнему не защищает от повторного участия одного человека — это не обещается.
