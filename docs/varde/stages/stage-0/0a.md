# Checkpoint 0a. Репозиторий и CI

Ветка `varde/0a` от `main`. Порядок: 0.1 → 0.2 → 0.2b → 0.3 → 0.4 → 0.4b. Общие правила — `stage-0.md`, раздел 2. Все команды ниже выполняются из `varde/`, если не сказано иное; пути `../docs/…` — относительно `varde/`. Никаких секретов в репозитории; `.env.example` — только имена переменных. Внешние инструменты (gitleaks, pg_dump 17, caddy) локально не установлены — scripts запускают их Docker-образами с закреплённым тегом.

## 0.2b Context-budget, lint обхода privacy (заглушка), границы импорта (2 ч)

**Цель.** CI валится на файле в 701 строку, на тестовом обходе `privacy` (по правильному правилу, не по чужой ошибке) и на нарушении границ импорта.

**Шаги.**

Пакет `tools/context-budget`: `check.mjs` обходит `varde/**` (исключая `node_modules`, `dist`, `coverage`, `**/prisma/migrations/**` — сгенерированный SQL, у папки свой `CLAUDE.md` с 0.4), расширения `ts tsx js mjs cjs css scss sql prisma`; файл > 700 строк → exit 1 с перечнем; > 500 — warning. `--selfcheck`: создаёт `tools/context-budget/.selfcheck/long.ts` в 701 строку, запускает проверку, ожидает exit 1, удаляет файл; при неудаче exit 1. 2. Пакет `tools/eslint-rules`, правило `varde/privacy-only-release` (заглушка до 0.15, но уже type-aware через `parserServices` typescript-eslint). Ошибка, если вне `apps/api/src/modules/privacy/**` и явного allow-списка: (а) любой доступ к свойству `response` или `aggregateSnapshot` у выражения, чей тип (включая составляющие intersection) называется `PrismaClient` или `TransactionClient` — любой метод, любое имя переменной (`prisma.`, `this.prisma.`, `tx.` внутри `$transaction`); (б) ключи `response`, `responses`, `aggregateSnapshot`, `aggregateSnapshots` в объектах `include`/`select` аргументов методов таких типов (чтение через связь); (в) `$queryRaw`, `$queryRawUnsafe`, `$executeRaw*` и `Prisma.sql`, чей текст содержит `response` или `aggregate_snapshot`; (г) импорт `PrismaService`/`@prisma/client` в `*.controller.ts` и `*.gateway.ts` (контроллеры тонкие, PRINCIPLES §12). Область — все пакеты workspace, где есть зависимость `@prisma/client`; allow-список в опциях правила фиксирован тестом: `apps/api/src/modules/privacy/**`, `apps/api/prisma/**`, и с этапа 1 — `modules/imports/**`, `modules/retention/**` (каждое исключение со своим тестом). Тест `RuleTester` (с type info): valid — тот же код под `modules/privacy/`; invalid — `prisma.response.findMany`, `this.prisma.response.count`, `tx.response.findMany` (`tx: TransactionClient`), `prisma.roundClient.findMany({ include: { responses: true } })`, `prisma.$queryRaw\`select * from response\``, `Prisma.sql\`… aggregate_snapshot …\``, `PrismaService` в `x.controller.ts`.
3. `pnpm lint:privacy:selfcheck` (`tools/eslint-rules/selfcheck.mjs`): копирует `tools/eslint-rules/fixtures/bypass.ts` (типизированная fixture без других ошибок lint: `this.prisma.response.findMany()` и `tx.response.findMany()`) в `apps/api/src/modules/__selfcheck__/bypass.ts`, запускает `eslint --format json` по этому файлу, требует хотя бы одно сообщение с `ruleId === 'varde/privacy-only-release'` (exit ≠ 0 по другой причине — провал selfcheck), удаляет копию; печатает `selfcheck: bypass rejected`.

## 0.4 Prisma: AuditLog, миграции в CI, seed (2 ч)

**Цель.** Prisma 6 в `apps/api`, первая миграция с `AuditLog`, `prisma migrate deploy` в CI и из прод-образа, миграция вперёд/назад на fixture-базе, идемпотентный seed.

**Читать.** `ARCHITECTURE.md` §4 строка `AuditLog`; `PRINCIPLES.md` §14 (локальный CLAUDE.md для миграций); `ADR-018` (миграции вперёд/назад); `ADR-025` строка про AuditLog `rows` («кто, объём, когда») — для поля `details`.

**Шаги.**
1. Версии закреплены: `prisma@6.x` и `@prisma/client@6.x` (одна мажорная; Prisma 7 меняет формат datasource и флаги `migrate diff` — не брать); `prisma` в `dependencies`, не `devDependencies` (CLI нужен в прод-образе для `migrate deploy`); generator `binaryTargets = ["native", "linux-musl-openssl-3.0.x"]` (образ на alpine); в `varde/pnpm-workspace.yaml` — `allowBuilds: { prisma: true, '@prisma/engines': true, '@prisma/client': true }` (pnpm ≥ 10 без этого не выполняет их postinstall — engines не скачиваются; поле `pnpm.onlyBuiltDependencies` в `package.json` pnpm 11 игнорирует, 0.1), в Dockerfile после `pnpm deploy` — `prisma generate` в `/out` (0.2 п. 3).
2. `apps/api/prisma/schema.prisma`: `AuditLog { id uuid pk default gen_random_uuid(); at timestamptz default now(); who text; what text; target text?; details jsonb? }`, индексы `(at)`, `(what, at)`. `details` — расширение «who, what, when, target» для объёма выдачи (ADR-025, ARCHITECTURE §4); секретов и ответов респондентов в `details` не бывает (правило в комментарии схемы; тест в 0.15).
3. `PrismaService` (`apps/api/src/prisma/prisma.service.ts`): подключается лениво (при первом запросе, не в `onModuleInit`) — приложение стартует без базы (job `image`, `/health` → 503 в 0.6); `connection_limit` **добавляет сам PrismaService** к `DATABASE_URL` из env (`bootstrap.sh` 0.5b пишет URL без него — число задаётся в одном месте) из `varde/config/db-budget.json` (создать: `{ "role_connection_limit": 20, "prisma_pool": 8, "pgboss_pool": 4, "reserve": 8 }` — используется в 0.5 и 0.9); каталог конфигов — `VARDE_CONFIG_DIR` (в `.env.example` без значения; по умолчанию `varde/config` относительно workspace, в образе `/out/config` — 0.2 п. 3).
4. Миграции: `prisma/migrations/<ts>_audit_log/migration.sql` плюс рукописный `down.sql` рядом (Prisma down-миграций не генерирует). Правило: последняя строка каждого `down.sql` — `DELETE FROM "_prisma_migrations" WHERE migration_name = '<имя папки>';`, иначе повторный `migrate deploy` ответит «No pending migrations». `prisma/migrations/CLAUDE.md`: «сгенерировано, не читать целиком; у каждой миграции есть down.sql, который заканчивается удалением своей записи из `_prisma_migrations`».
5. Seed `prisma/seed.ts`: идемпотентен (upsert по фиксированному id записи `what = 'seed.run'`); в этапе 0 данных нет.
6. Локальный Postgres для разработки: `infra/compose.dev.yml` (postgres:17.6-bookworm, порт 127.0.0.1:5433, тестовый пароль в файле — это dev-литерал, не секрет; БД `varde_dev`).
7. Scripts api: `db:migrate` (`prisma migrate deploy`), `db:seed`, `test:integration` (vitest с `DATABASE_URL`). В прод-образе та же команда — `node node_modules/prisma/build/index.js migrate deploy` (используется в `infra/README.md` 0.6 и `restore.sh` 0.10c); job `image` с этого коммита выполняет настоящий `migrate deploy` из образа против service Postgres (0.2 п. 1) — `--version` ничего не доказывает.

**Тесты (integration, Postgres).** `test/migrations.test.ts`: на пустой базе `migrate deploy` → применены все; затем `down.sql` в обратном порядке → `prisma migrate diff --from-url "$DATABASE_URL" --to-empty --exit-code` → exit 0 (пусто); снова deploy → `prisma migrate diff --from-url "$DATABASE_URL" --to-schema-datamodel prisma/schema.prisma --exit-code` → exit 0 («No difference detected»); `test/audit-log.test.ts`: запись и чтение; `test/seed.test.ts`: два запуска → одна строка `seed.run`; `test/prisma-lazy.test.ts`: `AppModule` создаётся с недоступным `DATABASE_URL`.

**Приёмка.**
```
docker compose -f infra/compose.dev.yml up -d
DATABASE_URL=<dev> pnpm --filter @varde/api db:migrate      # "1 migration applied" при первом запуске
DATABASE_URL=<dev> pnpm --filter @varde/api test:integration   # 4 файла, зелёные
```

**Не входит.** Любые другие модели (1.4a–c), триггеры immutability (1.4a/1.4c), pg-boss (0.9).
