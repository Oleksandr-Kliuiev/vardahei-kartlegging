## 0.5 База `varde`, роли, схема аудита (2 ч)

**Читать.** `ADR-016` решение, строка 1; `ADR-021` таблица «Доверенные субъекты»; `ADR-003` (роль `varde_app`, лимит соединений); `varde/config/db-budget.json` (0.4).

**Кодер.**
1. `infra/sql/varde-roles.sql` — уровень инстанса, выполняется superuser-ом в базе `postgres`; psql-переменные: `app_pw`, `backup_pw`, `dbname` (по умолчанию `varde`; CI подставляет другое имя), `role_limit` (из db-budget). Первые строки: `SET log_statement = 'none'; SET log_min_error_statement = 'panic'; SET log_min_duration_statement = -1;` — statement с паролем не попадает в серверный лог. Содержание: `CREATE ROLE varde_app LOGIN CONNECTION LIMIT :role_limit PASSWORD :'app_pw'` (сервер хранит SCRAM-verifier — `password_encryption` в PG17 по умолчанию `scram-sha-256`); `CREATE ROLE varde_backup LOGIN CONNECTION LIMIT 3 PASSWORD :'backup_pw'`; `CREATE ROLE varde_audit_owner NOLOGIN`; `CREATE DATABASE :dbname OWNER varde_app`; `REVOKE CONNECT ON DATABASE :dbname FROM PUBLIC`; `GRANT CONNECT … TO varde_app, varde_backup`. Повтор файла падает на `already exists` — это и есть защита от двойного запуска.
2. `infra/sql/varde-db.sql` — внутри базы, superuser: `GRANT USAGE ON SCHEMA public TO varde_backup`; `ALTER DEFAULT PRIVILEGES FOR ROLE varde_app GRANT SELECT ON TABLES TO varde_backup`, то же `ON SEQUENCES`, и `… GRANT USAGE ON SCHEMAS TO varde_backup` — всё **без** `IN SCHEMA`, чтобы покрыть схему `pgboss` (0.9) и любую будущую; **схема аудита**: `CREATE SCHEMA varde_audit AUTHORIZATION varde_audit_owner; REVOKE ALL ON SCHEMA varde_audit FROM PUBLIC; GRANT USAGE ON SCHEMA varde_audit TO varde_backup;` таблица `varde_audit.connection_log(at, role_name, application_name, client_addr, backend_pid)` с владельцем `varde_audit_owner`, `GRANT SELECT ON varde_audit.connection_log TO varde_backup`; `GRANT USAGE ON SCHEMA varde_audit TO varde_app` — только USAGE, иначе вызов `prune()` даёт `permission denied for schema` (владелец базы владеет `public`, но не `varde_audit`, и не может удалить таблицу или функцию); функция `varde_audit.log_login()` SECURITY DEFINER, владелец `varde_audit_owner`, `SET search_path = varde_audit, pg_catalog, pg_temp`, тело `BEGIN INSERT … EXCEPTION WHEN OTHERS THEN RAISE WARNING 'varde_audit: %', SQLERRM; END` (вход не блокируется, сбой виден в логе сервера); `CREATE EVENT TRIGGER varde_login ON login EXECUTE FUNCTION varde_audit.log_login()` (PG17; срабатывает только для подключений к этой базе); функция `varde_audit.prune()` SECURITY DEFINER, владелец `varde_audit_owner`, удаляет строки `at < now() − interval '12 months'` (срок зашит в функции), `REVOKE EXECUTE ON FUNCTION varde_audit.prune() FROM PUBLIC; GRANT EXECUTE ON FUNCTION varde_audit.prune() TO varde_app` (по умолчанию EXECUTE есть у PUBLIC, и read-only `varde_backup` с её USAGE могла бы чистить журнал; `log_login()` возвращает `event_trigger` и напрямую не вызывается) — её вызывает retention-job 1.31 (класс `connection_log` в 0.19); ничего другого в схеме `varde_app` не может. Комментарий в файле: `pg_read_all_data` ролям Varde не выдаётся никогда — она читает базы Atlas; superuser обходит триггер через `event_triggers=false`, поэтому держатели superuser (Vardahei) входят в доверенный круг ADR-021 поимённо.
3. Integration-тест в CI (service Postgres, superuser есть): `apps/api/test/db-roles.test.ts` выполняет `varde-roles.sql` и `varde-db.sql` с тестовыми паролями в базу `varde_t`, создаёт роль `atlas_test LOGIN`, в `afterAll` выполняет `varde-teardown.sql` (0.5b; роли общие для кластера — каждый тест, создающий роли Varde на service Postgres, убирает их за собой), и проверяет: (1) `atlas_test` → `varde_t`: `permission denied for database`; (2) `varde_backup`: `INSERT INTO varde_audit.connection_log` → `permission denied`, `SELECT` работает; (3) подключение `varde_app` увеличивает `count(*)` на 1 с `role_name = 'varde_app'`; (4) `rolconnlimit` `varde_app` = `role_connection_limit`, роли не члены `pg_read_all_data`; (5) от `varde_app`: `DROP TABLE varde_audit.connection_log`, `DELETE FROM varde_audit.connection_log`, `DROP FUNCTION varde_audit.log_login() CASCADE` → `permission denied`, после попыток триггер продолжает писать; (6) `varde_app` создаёт схему `q`, таблицу и sequence в ней — `pg_dump -Fc` ролью `varde_backup` (образ `postgres:17.6-bookworm`, `--network host`) → exit 0; (7) `varde_audit.prune()` от `varde_app`: строка с `at = now() − interval '13 months'` (вставлена superuser-ом) удалена, строка `now() − interval '1 day'` осталась; от `varde_backup` → `permission denied for function`.
4. `apps/api/.env.example` (канонический, единственный для api): `DATABASE_URL=` без значения; комментарий, что файл с credentials на VPS — `0600 root`, пишет `bootstrap.sh`, держатели перечислены в evidence.

**Приёмка.** `pnpm --filter @varde/api test:integration -- db-roles` → 7 тестов зелёные.
**Не входит.** `bootstrap.sh`, pg_hba и runbook (0.5b), pg-boss (0.9), бэкап-скрипты (0.10), таблицы приложения, retention-job для `connection_log` (1.31).
**Зависимости.** 0.4.

## 0.5b `bootstrap.sh`, изоляция от Atlas, runbook хостинг-оператора (1 ч)

**Читать.** `stage-0.md` §9 п. 5; `ADR-016` решение, строка 1; результат 0.5.

**Кодер.**
1. `infra/sql/bootstrap.sh` — выполняет хостинг-оператор на VPS от root: `set -euo pipefail`; **preflight** — `select 1 from pg_roles where rolname in ('varde_app','varde_backup')` через superuser-сессию: роль уже есть → exit 2 с текстом `run varde-teardown.sql first`, файлы не трогаются (повтор после частичного сбоя не разводит пароли в env и в базе); `role_limit` читает из `/opt/varde/config/db-budget.json` командой `docker run --rm -v /opt/varde/config:/c:ro node:22-alpine node -p 'require("/c/db-budget.json").role_connection_limit'` (`jq` на VPS не гарантирован); генерирует `app_pw`, `backup_pw` (`openssl rand -hex 32` — только `[0-9a-f]`, в `DATABASE_URL` без экранирования; `-base64` дал бы `/`, `+`, `=`) и, если в `app.env` ещё нет, `SESSION_SECRET` (`openssl rand -hex 48`) — всё в памяти; подаёт `\set app_pw …`, `\set backup_pw …`, `\set role_limit …` + `varde-roles.sql` на stdin `docker exec -i atlas-db-1 sh -c 'psql -U "$POSTGRES_USER" -d postgres -v ON_ERROR_STOP=1'`, затем `varde-db.sql` с `-d varde`; **только после успеха** обоих psql дописывает (`umask 077`) `/etc/varde/app.env` (`DATABASE_URL=postgresql://varde_app:<pw>@atlas-db-1:5432/varde` **без** `connection_limit` — его добавляет PrismaService из db-budget, 0.4 п. 3; `SESSION_SECRET=`) и `/etc/varde/backup.env` (`PGHOST=atlas-db-1`, `PGUSER=varde_backup`, `PGPASSWORD=`, `PGDATABASE=varde`), остальные ключи файлов не трогает; печатает только `bootstrap ok` или имя упавшего шага; пароли не попадают в argv, stdout, history и логи. Команда psql — переменная `VARDE_PSQL_CMD` (по умолчанию `docker exec …`; тест подставляет локальный `psql`). Тот же генератор паролей — в `restore.sh` (0.10c).
2. `infra/sql/varde-teardown.sql` — откат до появления данных: `DROP DATABASE varde; DROP ROLE varde_app, varde_backup, varde_audit_owner`.
3. `infra/sql/pg_hba.varde.conf` — три строки для вставки **перед** общими `host`-строками действующего pg_hba (решение 13.10 «Изоляция базы `varde`», `docs/BESLUTNINGER.md`): `host varde varde_app,varde_backup all scram-sha-256`, `host all varde_app,varde_backup all reject`, `host varde all all reject`. TCP-вход в `varde` остаётся только у ролей Varde; роли Varde по TCP не входят никуда, кроме `varde`; строк `local … reject` нет — unix-socket внутри контейнера остаётся единственным каналом superuser-обслуживания. Одна процедура при любом результате проверки `rolsuper` роли Atlas: пакет свёл два варианта ADR-016 (REVOKE / reject) к одной правке pg_hba — строка `host varde all all reject` обязательна в обоих вариантах по решению 13.10 и сама закрывает `varde` от любой не-Varde роли, включая superuser-роли, а TCP-доступ ролей Varde к базам Atlas закрывает вторая строка; REVOKE/GRANT CONNECT на базах Atlas не делается (не нужен и рискует молча отрезать роль Atlas, не подключённую в момент проверки); `varde` дополнительно закрыта от PUBLIC в `varde-roles.sql`, что покрывает и socket для не-superuser ролей.
4. `infra/sql/README.md` (по-русски — runbook хостинг-оператора; первая строка: все superuser-шаги к `varde` — только через unix-socket, `docker exec … psql` без `-h`): (а) **read-only до bootstrap**: `rolsuper` роли приложения Atlas — `psql -tAc "select distinct usename, rolsuper from pg_stat_activity join pg_roles on rolname = usename where backend_type = 'client backend' and pid <> pg_backend_pid()"` (нужно только для записи остаточного риска §9 п. 5, на процедуру не влияет); `SHOW hba_file` (действующий файл может быть не `$PGDATA/pg_hba.conf`); `SHOW max_connections`, `select count(*) from pg_stat_activity` — если запаса под 20 + 3 нет, `role_connection_limit` в db-budget снижается коммитом кодера до bootstrap. (б) `bootstrap.sh`. (в) **pg_hba**: копия файла из `SHOW hba_file` → `pg_hba.conf.bak-<ts>`; вставка `pg_hba.varde.conf` перед первой общей `host`-строкой (файл в томе данных Postgres переживает передеплой Atlas — initdb на существующем томе его не перезаписывает; если файл — read-only bind-mount с хоста, остановиться и вынести вопрос в evidence: путь на хосте без `docker inspect` не определяется); `select pg_reload_conf()`; `select count(*) from pg_hba_file_rules where error is not null` → `0`; проверки: superuser по socket `psql -d varde -c 'select 1'` → ok; `psql -h 127.0.0.1 -U "$POSTGRES_USER" -d varde -c 'select 1'` внутри контейнера → `pg_hba.conf rejects connection` (reject срабатывает до аутентификации, пароль не нужен); после первого деплоя (контейнеры из 0.6/0.10): `docker compose -f /opt/varde/compose.yml run --rm backup psql -c 'select 1'` → ok, `… run --rm backup psql -d postgres -c 'select 1'` → `rejects connection`; откат — вернуть `.bak`, reload. ## 0.9 pg-boss с лимитами (2 ч)

**Читать.** `ADR-003`; `ARCHITECTURE.md` §2 абзац «Фоновые задачи»; `varde/config/db-budget.json`.

**Шаги.**
1. `apps/api/src/jobs/`: `job-config.ts` — реестр типов задач с обязательными полями `{ name, concurrency, timeoutSeconds, retryLimit, retryBackoff: 'exponential', retryDelaySeconds, policy: 'stately' | 'singleton', idempotency: (payload) => string }`; значения по умолчанию в конфиге (не в коде): `concurrency 1`, `timeoutSeconds 60`, `retryLimit 3`, `retryDelaySeconds 10`, `policy 'stately'`; тест переопределяет через конфиг (`retryDelaySeconds 1`, `timeoutSeconds 2`). В этапе 0 два типа: `demo.sleep` (для тестов) и `demo.hold-connection` (для стенда 0.12: держит транзакцию и ждёт `GET /stub/slow` 20 с — обязательно `prisma.$transaction(fn, { timeout: 30_000, maxWait: 5_000 })`: по умолчанию интерактивная транзакция Prisma закрывается через 5 с, задача падала бы и отпускала соединение раньше, а стенд недооценивал бы нагрузку на пул; URL ожидания — из конфига, чтобы тест 0.12 мог подставить mock).
2. `jobs.service.ts`: pg-boss 10 в базе `varde` под `varde_app` (schema `pgboss`), `max = pgboss_pool` из db-budget; `archiveCompletedAfterSeconds` = 12 ч, `deleteAfterDays` = 7 (класс `pgboss_jobs` в 0.19); очереди создаются при старте `createQueue(name, { policy, … })`. Семантика policy в pg-boss 10 (ни одна не даёт «одна задача на ключ, включая `active`»): `stately` — на один `singletonKey` одна задача в `created`/`retry` **плюс** одна `active`, то есть задача с тем же ключом может в это время выполняться — поэтому обработчики обязаны быть идемпотентными (повтор с тем же payload не меняет результат); `singleton` — очередь без ограничения, но две задачи с одним `singletonKey` никогда не выполняются **одновременно** (вторая остаётся `created`, пока первая не завершится); для типов, где параллельный повтор недопустим, в конфиге `policy: 'singleton'`. `enqueue(name, payload)` валидирует payload строгой zod-схемой `{ id: uuid, hash?: /^[a-f0-9]{64}$/ }` (`.strict()`) — другие ключи, JSON в `hash` или строка иной длины отклоняются с `JobPayloadRejected`; `singletonKey` = `idempotency(payload)`.
3. Бюджет соединений: `apps/api/src/config/db-budget.ts` читает `varde/config/db-budget.json`; `test/db-budget.test.ts`: `prisma_pool + pgboss_pool ≤ role_connection_limit − reserve`; PrismaService и pg-boss берут числа только оттуда (grep-тест: литералов `connection_limit=` в `src/` нет).

**Тесты (integration).** `test/jobs.test.ts`: `demo.sleep` с `timeoutSeconds = 2` и работой 5 с → задача `failed` после `retryLimit + 1` попыток (счётчик вызовов = 4), интервалы растут; тот же `singletonKey` дважды при `created` → одна задача; после `completed` → новая; тип с `policy: 'singleton'`: пока первая задача `active`, второй `send` с тем же ключом создаёт задачу в `created`, и она не становится `active`, пока первая не завершится (опрос `getJobById`; счётчик одновременных вызовов обработчика ≤ 1); payload с полем `answers` → `JobPayloadRejected`; `hash` = JSON-строка → `JobPayloadRejected`; после старта pg-boss `pg_dump -Fc` ролью `varde_backup` (как в 0.5 п. 3) → exit 0 (схема `pgboss` покрыта default privileges); `db-budget.test.ts`.

**Приёмка.** `pnpm --filter @varde/api test:integration -- jobs db-budget` → зелёные; `cat config/db-budget.json` в evidence.

## 0.8 Break-glass (3 ч)

**Читать.** `ADR-008` решение, строка 2; `ARCHITECTURE.md` §3 строка «Break-glass»; `ADR-021` «Доверенные субъекты»; `stage-0.md` §9 п. 9.

**Кодер.**
1. Включение: `VARDE_BREAK_GLASS_UNTIL=<ISO-время>`, `VARDE_BREAK_GLASS_PASSWORD_HASH='<argon2id>'` — **обязательно в одинарных кавычках**: `app.env` — `env_file` Compose, а Compose v2 интерполирует `$VAR` в значениях без кавычек и в двойных кавычках, и PHC-строка `$argon2id$v=19$m=…` превратилась бы в мусор (verify всегда неверен); приложение при старте проверяет, что hash начинается с `$argon2id$`, иначе функция не включается и пишется `break_glass.rejected` (`details: {reason: 'bad_hash'}`); `VARDE_BREAK_GLASS_OPERATOR=<имя>` (кто из держателей SSH включил; `who = 'break-glass:<имя>'`). Без переменных или при `now ≥ UNTIL` функция выключена: второй listener не поднимается, на основном listener `/break-glass/*` → `404` всегда. `UNTIL > now + BREAK_GLASS_MAX_HOURS` (по умолчанию 4) → функция не включается, AuditLog `break_glass.rejected` (`details: {until}`). Таймер: в момент `UNTIL` listener закрывается, все сессии `via = break_glass` отзываются.
2. Listener — **Unix socket** `VARDE_BREAK_GLASS_SOCKET` (по умолчанию `/run/varde/break-glass.sock` в контейнере; каталог хоста `/var/lib/varde/run`, `2770` с setgid, владелец uid 1000, группа docker — создаёт деплой 0.6, bind в длинной форме без `create_host_path`), не TCP: контейнер в сетях `atlas_edge`/`atlas_internal` не выставляет порт соседним контейнерам. Перед `listen` устаревший файл socket (остался после падения или OOM — каталог не tmpfs) удаляется; после `listen` — `chmod 0660` на socket (Node создаёт его по umask как `0755`, без права записи у группы connect невозможен; группу даёт setgid каталога). Доступ `ssh -L 3001:/var/lib/varde/run/break-glass.sock vardahei-vps` пользователем root или из группы docker (sshd открывает socket от имени SSH-пользователя); на проде это держатели SSH — сегодня Oleksandr и хостинг-оператор; у заместителей SSH нет и по решению 13.10 «Escrow прод-секретов … не делаем» не планируется. Второй экземпляр приложения на socket обслуживает весь admin API и статику админки плюс `POST /break-glass/login` (пароль → argon2 verify) — выдаёт сессию `via = break_glass` (таблица 0.7) со сроком `min(UNTIL, now + 1h)`; `AdminSessionGuard` принимает её только на этом listener; cookie выдан на `localhost:3001` и через туннель работает. Запись `break_glass.login` в AuditLog и создание сессии — одна транзакция: сбой записи → сессии нет.
3. AuditLog: `break_glass.enabled` при старте с активным флагом (`details: {until, operator}`), `break_glass.rejected`, `break_glass.login`, `break_glass.login_failed`, `break_glass.closed` (таймер).
