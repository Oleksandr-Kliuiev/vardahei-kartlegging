# Checkpoint 0c. Контракты

Ветка `varde/0c` от `main` после merge 0b. Порядок выполнения отличается от нумерации: **0.16 → 0.15 → 0.15b → 0.17 → 0.19 → 0.18 → 0.19b** — privacy опирается на типы из `packages/schema`, поэтому схема идёт первой. Правило для входов, которых может не быть к концу checkpoint (одно и то же в `STAGES.md`): 0.17 без OpenAPI закрывается как `draft — ждёт OpenAPI` (OpenAPI и пример берёт хостинг-оператор (Claude) из репозитория Atlas — внутренней платформы Vardahei, решение 13.10; принятие — до 4.4); 0.18 без утверждения Oleksandr остаётся задачей со статусом `pending` при зелёных тестах — checkpoint 0c закрывается с этим статусом, задача 0.18 принимается после утверждения отдельным evidence, утверждение нужно к 1.13d (ворота G2).

Как 0c работает без таблиц этапа 1 (Round, Response, MetricDefinition, AggregateSnapshot появляются в Prisma в 1.4b/1.4c): модуль `privacy` и `release()` работают над интерфейсами (`ResponseSource`, `SnapshotStore`) с in-memory реализациями в тестах; транзакция «AuditLog в одной транзакции с ответом» — настоящая, на Prisma и AuditLog из 0.4; неизменяемость released — на уровне типов и state-machine в 0.16, триггер БД — 1.4c. Реальные HTTP-маршруты дашборда — 1.27/1.27b; в 0c `401`/`404` проверяются на тестовом контроллере в `apps/api/test/support/`, который монтирует сервис privacy за `AdminSessionGuard` из 0.7.

## 0.15b `privacy.release()` с историей выдач (3 ч)

**Читать.** `ADR-021` раздел «Подавление с учётом истории выдач» (правила 1–6 и отрицательные тесты); `ADR-020` строка lifecycle; `aggregate-snapshot.ts` (0.16).

**Шаги.**
1. `release.ts`: `release(round, population, cells, store, actor)` — единица `(round, population, metric_version, group)` со значениями `(n, numerator)`; правила: (1) `n ≥ k`; (2) против каждого прежнего released той же `(round, population)` таблица разностей `Δn = 0` или `Δn ≥ k`, иначе carry-forward предыдущего значения с `stale = true` (в выдаче — только прежнее released значение, ничего из нового); (3) подавление дополнительных ячеек в разностях (`Δитог − Δроль A < k` → carry-forward и у итога или роли A); (4) набор метрик фиксируется при первом release — новая метрика к раунду с release → `ReleaseRejected`; (5) ручной release — та же функция с `actor` и записью AuditLog `privacy.release.manual`; автоматический (при закрытии раунда) — `privacy.release.auto`; (6) ячейки прогресса («обрыв по вопросу», «активные сессии») — те же правила; точный счётчик ответов на RoundClient — явное исключение `exact_counts: ['responses_total']`, тест фиксирует, что он не подавляется. Переход `computed → released` — module-private функция `markReleased` в `release.ts` (не экспортируется из модуля; lint 0.2b запрещает глубокие импорты в `modules/privacy/**`), единственный вызов — внутри `release()`.
2. `SnapshotStore` интерфейс (`listReleased`, `save`, `supersede`), in-memory в тестах; предыдущий released при новом release → `superseded` через `transition` с `reason = 'new release'`.
3. Живой вид админов (ADR-021: история выдач не применяется) — не через `release()`, а через `aggregate()` 0.15; тест, что `aggregate()` не пишет в `SnapshotStore`.

**Тесты (`release.test.ts`, по ADR-021:40).** `(3,3) → (4,3)` → ячейка carry-forward `stale` и в её JSON только прежние числа; итог +4 при роли A +3 и роли B +1 → роль B и одна из {итог, роль A} carry-forward; ручной release после одного нового ответа → ни одна ячейка ответов не меняется, AuditLog `privacy.release.manual` записан; обрыв по вопросу 2 → 3 → carry-forward до Δn ≥ k; добавление метрики к раунду с release → `ReleaseRejected`; предыдущий released → `superseded` с reason, старый не удалён; `responses_total` на RoundClient меняется точно; `release()` без `actor` → отклонено; `markReleased` недоступен из публичной поверхности модуля (тест импорта).

**Приёмка.** `pnpm --filter @varde/api test -- release` → ≥ 9 зелёных.
**Не входит.** Хранение в Prisma (1.4c), расчёт метрик (1.10), повтор на реальных эндпоинтах (1.32).
**Зависимости.** 0.15, 0.16.
