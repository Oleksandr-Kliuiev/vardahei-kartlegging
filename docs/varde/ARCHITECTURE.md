# Архитектура платформы Varde

Состояние после трёх раундов brainstorm (Fable ↔ Astra) и проверки одобрения, 11.10.2026, с delta 12.10 под изменения kartlegging (ADR-025, ADR-026 и правки существующих ADR; бриф — `astra/delta-12-10-brief.md`). Источник решений — `adr/`; этапы — `STAGES.md`; принципы — `PRINCIPLES.md`. Решения Oleksandr и Asbjørn по O1–O5 (12–13.10) внесены; открытых пометок в артефакте нет. Delta одобрена 13.10 (`astra/delta-12-10-approval.md`, non-blocking заметки внесены пакетом этапа 0); решения 13.10 о коде (папка `varde/` в этом репозитории) и заместителях для восстановления (Asbjørn, Bjarte) внесены; пакет этапа 0 — `stages/stage-0.md`.

## 1. Назначение

Одна платформа для цикла «опрос → выводы → семинар → опрос после» с шестью клиентами Vardahei. Ассистент готовит черновики (опросы, переводы, объяснения, пакеты семинаров) и никогда не публикует сам. kartlegging работает до конца текущей кампании; Varde строится рядом и впитывает его данные через доказуемый импорт.

Решения Oleksandr от 11.10, не обсуждаемые: без ролей (одна группа Entra); до пяти семинаров в год, без автоотправки почты; без SaaS и `org_id`; условия провайдера модели (с 13.10 — Anthropic API) проверяются в этапе 0. Решения 12.10 (`docs/BESLUTNINGER.md`, бриф delta §3): опросник по безопасности — 22 вопроса Forms дословно с обязательными инициалами (F1), зоны по Master_Analyse, без советов и сценариев; KI-опросник анонимный, с советами и сценарием; блок руководителя в обоих; ответы обоих опросников хранятся бессрочно и при уходе клиента остаются, удаление только по явному запросу; букмол — отдельным переключателем (заменяет «третьим языком с первого дня»); для опросника по безопасности граница доверия — вариант B спора 21: ответы по человеку видят только трое сотрудников Vardahei IT, клиент получает сводку без инициалов. Решения 13.10: анонимность выбирается перед стартом каждого опросника, по умолчанию опросники не анонимны; в обоих режимах трое админов видят все ответы (вариант B для всех опросников), анонимный режим защищает от клиента и внешних каналов; часть руководителя — правило (a); databehandleravtale покрывает опросники, по требованию клиента Vardahei возвращает или удаляет его данные.

## 2. Компоненты

```
Респонденты (телефон, ссылка с кодом)      Команда Vardahei (3, Entra)
            │                                        │
      Caddy atlas-edge (общий, TLS; query-string не логируется для runner)
            │
   Контейнер varde ──────────────────────────────────────────────

   │   seminars · imports · atlas · retention · auth                         │
   ────────────────────────────────────────────────────────────────
            │
   Postgres 17 (общий инстанс, своя база `varde`, свои роли)
            │                      │
```

Визуальный стиль — как в kartlegging (палитра, Atkinson Hyperlegible, высотный профиль с турgåar, палатка и костёр на финише), см. PRINCIPLES «Визуальный стиль». Языки runner: коды nn/nb/en поддерживаются, респонденту показываются языки версии шаблона — для клиентских опросов nn и en обязательны, nb по переключателю (ADR-019).

Код живёт в папке `varde/` этого репозитория (решение 13.10): `varde/apps/api`, `varde/apps/admin`, `varde/apps/runner`, `varde/packages/schema`, `varde/packages/rules`, `varde/infra` (Dockerfile, compose, SQL, бэкап, Caddy-блок), `varde/tools` (context-budget, eslint-правила, secrets, docs, invariants, нагрузка, метрики, eval), `varde/config` (бюджет соединений, privacy k, retention, модель) — свой pnpm workspace, Node 22 (NestJS 11 на Fastify, Prisma 6 — пакет этапа 0); `kartlegging/` рядом до cutover, его деплой не затрагивается (единственная правка до cutover — флаг read-only, 1.34). Пакеты: `packages/schema` (zod: шаблоны, API, Proposal-выходы), `packages/rules` (движок выражений и метрик) с прямыми entry points: `rules/runner` (видимость, зависимости вариантов, нормализация), `rules/findings` (метрики, правила выводов); корневого экспорта у `@varde/rules` нет. Barrel-файлов нет (ADR-004 не менялся, уточнение Astra); lint-правила границ — 0.2b.

Фоновые задачи: pg-boss в той же базе; concurrency, timeout, предел повторов, idempotency key, общий бюджет соединений Prisma/pg-boss; payload содержит ссылки на данные, не данные (ADR-003).

## 3. Вход и доступ

- Команда: OIDC через Entra, допуск по членству в одной группе, сессия в HttpOnly-cookie. Ролей нет.
- Break-glass: локальный админ, выключен по умолчанию; включается флагом окружения на ограниченное окно, слушает только локально на хосте VPS (Unix socket в каталоге хоста, не TCP — контейнер в общих сетях Atlas порт не выставляет; доступ через SSH-туннель на socket), сессия ограничена по времени, каждое включение и вход — в AuditLog (ADR-008, пакет этапа 0).
- Респонденты: ссылка с кодом RoundClient — случайный bearer ≥128 бит, с отзывом, сроком и перевыпуском. Код не попадает в логи Caddy и приложения (ADR-009). Личных токенов нет.
- Экран ведущего на семинаре: отдельный presenter-token, выпущенный заранее на семинар, чтобы день семинара не зависел от Entra (этап 3).
- Лимиты: отправки считаются по RoundClient (ожидаемая численность × запас) и глобально; per-IP лимит только как грубая защита от злоупотреблений с высоким порогом.

## 5. Приватность

Анонимность — свойство версии шаблона, не системы (ADR-025): `TemplateVersion.identification = initials` (по умолчанию; опросник по безопасности: обязательные инициалы F1, вид по сотруднику, сравнение по людям) или `none` (анонимный режим; сейчас KI-опросник) выбирается при публикации версии, до открытия раунда; раунд наследует режим. Модуль `privacy` — единственная точка выдачи для дашборда, CSV, экспорта, ассистента, отчётов и Atlas, с двумя классами. Класс `aggregate`, одинаковый в обоих режимах, для `part = common`: группа показывается при n ≥ 3; подавляются и дополнительные группы, восстанавливаемые вычитанием из итога; timestamps ответов хранятся с точностью до дня; прогресс наружу только суммарно; released-снимки создаются только через `privacy.release()` с подавлением по истории выдач: между любыми двумя released того же раунда Δn ячейки равно 0 или ≥ k, иначе ячейка повторяет предыдущее значение (carry-forward, `stale`); набор метрик раунда фиксируется при первом release; ручной release и ячейки прогресса идут тем же путём (ADR-021). Класс `rows`, в обоих режимах: строки общей части для трёх админов — только админ-сессия, каждое чтение в AuditLog, никогда в снимки, CSV для клиента, ассистента, Atlas и отчёт; в идентифицированных раундах строка несёт `respondent_key`, и на ней стоят вид по сотруднику (snittscore, зона, зона предыдущего раунда по паре «клиент + инициалы»), сравнение по людям и экспорт Master_Analyse; в анонимных раундах строки без ключа (роль, ответы, свободный текст), вид по сотруднику и экспорт Master_Analyse → 404. Часть руководителя (`part = leader`, 1–2 человека на клиента, по форме «ikkje anonymt», в обоих опросниках) не выдаётся вместе с общей частью (связь частей — `respondent_key` и `source_id` импорта — видна только админам, решение 13.10) и выдаётся вне порога по отдельному правилу ADR-021: эндпоинт по одному клиенту, только админ-сессия, каждое чтение в AuditLog, не попадает в снимки по клиенту, CSV, ассистент, Atlas и автоматический отчёт; единственная сводка — population `leaders_all` (все клиенты раунда вместе, под k) только для админ-дашборда при «alle» (ADR-020); правила FUNN по руководителю и кросс-правило F12×B13 идут leader-каналом (ADR-026); правило (a) подтверждено Oleksandr 13.10 как обещание респондентам. Таблица утечек (итог + видимая роль, малые клиенты, экспорт, timestamps, `respondent_key` и строки вне класса `rows`) — в тестах и в `REVIEW-CHECKLIST.md`.

Граница доверия — **вариант B для всех раундов** (решения Oleksandr 12.10 и 13.10, ADR-021): трое админов доверены под AuditLog, живые агрегаты с порогом в открытом раунде, класс `rows` в обоих режимах; клиент получает «samla bilete utan initialar» — агрегаты под k, выводы, сравнение с прошлым раундом, отчёт — и никаких строк; анонимный режим защищает от клиента и внешних каналов, не от админов; отдельного raw-экспорта нет. Вариант A и правило выбора — в истории ADR-021. `privacy` работает в двух режимах по `Round.identification`, различие — только `respondent_key` и то, что на нём держится.

Хранение по классам (ADR-017, решения 12.10): ответы обоих опросников — закрытые и свободный текст, common и leader, импортированные раунды — **бессрочно**; при уходе клиента остаются; удаление только по явному запросу — по клиенту, по человеку (обе части) или по найденным человеком строкам анонимного раунда — действием человека через `retention.forget` с записью в журнал удалений `DeletionLedger` (запрос + tombstones) и AuditLog, released-снимки при этом остаются; журнал экспортируется отдельно после каждой записи, применяется после restore, в импорте и при rollback, поэтому удалённое не возвращается ни из дампа, ни из `svar.jsonl`, ни из `runde1.js`; прогресс 24 ч; released-снимки ≥ 3 года; контакты — пока есть отношение и согласие; регистрации — семинар + 90 дней; Proposal и AuditLog — 12 месяцев; `DeletionLedger` — бессрочно; backup-копии — ротация 35 дней в `backup.sh` плюс до 93 дней корзины SharePoint (purge не подтверждается), поэтому удалённое по запросу исчезает из всех копий не позже чем через 128 дней (ADR-016, ADR-017). Импортированные данные kartlegging: raw в Varde бессрочно; `svar.jsonl` и `runde1.js` выносятся в зашифрованный архив в момент cutover (старое приложение — только redirect, без raw и без `/runde1.js`), архив удаляется после отчёта клиентам, но не позднее 90 дней после cutover; копии раунда 1 вне Varde чистит Oleksandr по tombstone из журнала (ADR-017). Решение 13.10: databehandleravtale покрывает опросники; по требованию клиента Vardahei возвращает все его данные (`retention.handover` — зашифрованный файл через класс `rows`, AuditLog) или удаляет их. Остаточный риск — не вопрос, а текст: право клиента на возврат строк по человеку расходится с сегодняшним обещанием «svara per person ser berre Vardahei IT»; уведомление v2 (0.18) говорит об этом прямо, текст утверждает Oleksandr (ADR-017). Уведомление респондентам v2 (nn/en, nb по переключателю) называет по режиму: инициалы и кто видит ответы по человеку, или «Vardahei IT ser svara, men ikkje kven som svarte»; критерий хранения и удаление по запросу; право клиента требовать выдачи или удаления; факт обработки агрегатов моделью; «ответы руководителя не анонимны»; роли сторон.

## 6. Ассистент

Набор умений с типизированным выходом по `packages/schema`; результат всегда Proposal. Один провайдер — Anthropic API (Claude; модель по умолчанию `claude-opus-5-5`, решение Oleksandr 13.10), за тонким адаптером с интерфейсом «структурированный вывод, инструменты, стоимость» (ADR-010). Второй провайдер — только после подтверждённой потребности и своей проверки условий.

Что видит: агрегаты и выводы через `privacy` классом `aggregate`; выдержки из свободных ответов, подготовленные человеком и помеченные как проверенные; стилевой гайд, глоссарий, библиотеку вопросов. Никогда: инициалы, `respondent_key`, строки по человеку и строки руководителя — сборщик контекста это отклоняет (ADR-011, ADR-025). Замороженные якоря (`frozen`) умения «Редактура вопроса» и «Черновик по брифу» не трогают (ADR-005). Автоматическая обработка сырого свободного текста в v1 отсутствует (ADR-011). Инструменты только на чтение; запись только в Proposal.

Качество: автопроверки черновика (схема, выход «veit ikkje» или skip, стоп-список продуктов, ≤25 слов на вопрос без учёта текста сценария, сценарий с ответом и пояснением, все требуемые языки или пометка «к переводу») — к вопросам с `frozen` (ADR-005) стоп-список и лимит слов не применяются ни в черновике, ни в переводе, ни в eval: F20 длиннее 25 слов, F17 называет OneDrive/SharePoint, так решил шеф; у них проверяется только дословность якоря (hash) и принятие перевода; проверка форм nn/nb; золотой набор из 10 брифов на записанных ответах в CI; живой прогон при смене любого из `(prompt_hash, model, briefs_version)` и перед приёмкой этапа, не ночной (ADR-018); статистика принятия. Semantic validation: цифры в тексте должны ссылаться на released-снимок. Допуск к модели — ворота G0 (checkpoint 0d с порогами из ADR-010), допуск к ассистенту в продукте — ворота G1 (одна настоящая кампания на Varde), см. `STAGES.md`.

Лимиты стоимости в день и на пользователя. Длинные задачи — через pg-boss, уведомление в админку по SSE.

## 7. Семинары (этап 3)

Seminar рождается из Findings и ссылается на раунды before/live/after. Регистрация — страница с именем, компанией, почтой, ICS; приглашение отправляет человек из своей почты (навсегда, не «пока»). Живой опрос — тот же runner в live-режиме; состояние вопросов (open → closed → released) ведёт сервер; экран ведущего получает по SSE только released-результаты и при reconnect восстанавливается из snapshot (ADR-015). Сравнение «до/после» показывает наблюдаемую динамику с оговорками (состав ответивших, самоотбор), без заявления причинного эффекта.

## 8. Живое обновление

SSE. Админка получает событие «изменилось» и перечитывает состояние через обычный API. Экран ведущего — отдельный поток с разрешёнными данными конкретного live poll.

## 9. Размещение и эксплуатация

Тот же VPS, Docker, за Caddy atlas-edge. База `varde` с ролями `varde_app` и `varde_backup` (read-only); TCP-вход в `varde` закрыт для всех ролей, кроме ролей Varde (три строки pg_hba, решение 13.10), credentials независимы. Ночной `pg_dump` → шифрование (age; приватные ключи без пароля на зашифрованных дисках Oleksandr и заместителей Asbjørn и Bjarte, решения 13.10) → rclone в отдельный сайт SharePoint `VardeBackup` (app-only с client secret), ротация 35 дней в `backup.sh` плюс до 93 дней корзины; журнал удалений (`DeletionLedger`) экспортируется тем же путём отдельным файлом сразу после каждой записи; restore-скрипт и runbook на нюношке для заместителей; восстановление = дамп + применение последнего экспорта журнала, после чего повторно запускается удаление просроченных данных (ADR-016, ADR-017). Целевых RPO/RTO нет, restore-drill на чистой машине отложен — остаточный риск «бэкап не проверен восстановлением» принят Oleksandr 13.10 (ADR-016). Действия на хостинге выполняет хостинг-оператор (Claude; в `docs/BESLUTNINGER.md` — «Claude-оркестратор») по runbook-шагам пакета этапа; кодер доступа к VPS и секретам не получает (решение 13.10, PRINCIPLES §20). Ёмкость VPS измеряется в этапе 0 (неделя метрик, нагрузка 100 телефонов + бэкап + AI-задача; критерий: без OOM, ≥25 % RAM в запасе, p95 отправки < 1 с, Atlas не деградирует); при провале сначала выносятся необязательные workloads.

## 10. Импорт и переключение

ImportManifest с hash источника как контролем целостности; `source_id` у обеих частей равен постоянному `id` строки `svar.jsonl` (для раунда 1 — ключу записи `(k, init)`), а не hash содержимого, уникальность по `(source_id, part)`, поэтому identity переживает очистку при rollback и не зависит от разбиения импорта на проходы; подавление при любом импорте по частям и только по журналу удалений: `suppressed` по `(source_id, part)`, уже импортированные — `existing`; Submission API сверяет `submission_id` с журналом; таблица всех путей возврата удалённого — ADR-024; сверка по счётчикам по частям (accepted + rejected + existing + suppressed), идемпотентный повтор, отчёт отклонённых; сверка со старым дашбордом — за вычетом записей журнала; при rollback cutover журнал применяется к восстановленному архиву (`svar.jsonl` и `runde1.js`): строка целиком — по tombstone common-части, часть руководителя — по tombstone leader-части, `id` очищенной строки не меняется; полный цикл удаление → rollback → повторный cutover репетируется в 1.34. `svar.jsonl` → Response раунда 2 (для опросника по безопасности `F1` → `respondent_key`); Forms (`runde1.js`, 57 ответов по людям) → Round 1 типа `external_import` с `identification = initials` и common Response с `respondent_key` — не снимки (ADR-024, изменено 12.10): сравнение по людям и экспорт для шефа требуют строк. Метрики по F-якорям `comparable` с пояснением (ADR-020). Паритет проверяется на согласованных fixtures (синтетические инициалы) с перечнем намеренных исправлений; сверка с настоящими файлами — только числами в evidence. Production cutover — отдельная задача с чек-листом: стоп записи в kartlegging, финальный импорт и сверка, go/no-go с подписью Oleksandr, DNS, rollback до 7 дней с сохранением ответов, принятых Varde; после rollback kartlegging работает только на чтение, приём заново не открывается — сбор ответов в это окно идёт новым раундом в Varde (ADR-024). Нагрузочный тест настоящего Submission API — перед cutover (ADR-016).

## 11. Тесты

`packages/rules` — табличные юнит-тесты (включая truthiness пустых значений, choices_from, exclusivity); API — интеграционные на Postgres в контейнере; runner и admin — Playwright; инварианты — обход privacy, `respondent_key` и строки вне класса `rows`, вид по сотруднику → 404 для анонимного раунда, identifier вне `answers`, величины из строк leader вне `leaders_all` и `leaders_all` вне внешних каналов, удалённое по запросу не возвращается импортом, rollback и restore с журналом, replay отправки, потеря HTTP-ответа после commit, миграции, семантика ветвления; ассистент — записанные fixtures в CI, живой прогон по триггеру. Context-budget тест: ни один файл source/test/e2e/css в `varde/**` не длиннее 700 строк (`kartlegging/` — legacy вне бюджета; сгенерированные миграции и data-fixtures не считаются, 0.2b).
