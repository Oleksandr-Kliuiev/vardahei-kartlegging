# Архитектура платформы Varde

Состояние после трёх раундов brainstorm (Fable ↔ Astra) и проверки одобрения, 11.10.2026, с delta 12.10 под изменения kartlegging (ADR-025, ADR-026 и правки существующих ADR; бриф — `astra/delta-12-10-brief.md`). Источник решений — `adr/`; этапы — `STAGES.md`; принципы — `PRINCIPLES.md`. Открытые места помечены **[O3]**, **[O4]**, **[O5]** и ждут ответов Oleksandr и Asbjørn.

## 1. Назначение

Одна платформа для цикла «опрос → выводы → семинар → опрос после» с шестью клиентами Vardahei. Ассистент готовит черновики (опросы, переводы, объяснения, пакеты семинаров) и никогда не публикует сам. kartlegging работает до конца текущей кампании; Varde строится рядом и впитывает его данные через доказуемый импорт.

Решения Oleksandr от 11.10, не обсуждаемые: без ролей (одна группа Entra); до пяти семинаров в год, без автоотправки почты; без SaaS и `org_id`; условия Azure OpenAI проверяются в этапе 0. Решения 12.10 (`docs/BESLUTNINGER.md`, бриф delta §3): опросник по безопасности — 22 вопроса Forms дословно с обязательными инициалами (F1), зоны по Master_Analyse, без советов и сценариев; KI-опросник анонимный, с советами и сценарием; блок руководителя в обоих; ответы обоих опросников хранятся бессрочно и при уходе клиента остаются, удаление только по явному запросу; букмол — отдельным переключателем (заменяет «третьим языком с первого дня»); для опросника по безопасности граница доверия — вариант B спора 21: ответы по человеку видят только трое сотрудников Vardahei IT, клиент получает сводку без инициалов.

## 2. Компоненты

```
Респонденты (телефон, ссылка с кодом)      Команда Vardahei (3, Entra)
            │                                        │
      Caddy atlas-edge (общий, TLS; query-string не логируется для runner)
            │
   Контейнер varde ──────────────────────────────────────────────
   │ apps/runner  Preact/vanilla ≤100 KB gz, nn/nb/en, draft в localStorage │
   │ apps/admin   React + Vite + TS, TanStack Query, UI на нюношке           │
   │ apps/api     NestJS + Prisma; pg-boss; модули по доменам                │
   │   privacy · surveys · rounds · metrics · findings · assistant           │
   │   seminars · imports · atlas · retention · auth                         │
   ────────────────────────────────────────────────────────────────
            │
   Postgres 17 (общий инстанс, своя база `varde`, свои роли)
            │                      │
   Atlas (API: список клиентов → ; ← observations)    Azure OpenAI (EU, один deployment)
```

Визуальный стиль — как в kartlegging (палитра, Atkinson Hyperlegible, высотный профиль с турgåar, палатка и костёр на финише), см. PRINCIPLES «Визуальный стиль». Языки runner: коды nn/nb/en поддерживаются, респонденту показываются языки версии шаблона — nn обязателен, en и nb по переключателю (ADR-019).

Пакеты: `packages/schema` (zod: шаблоны, API, Proposal-выходы), `packages/rules` (движок выражений и метрик) с прямыми entry points: `rules/runner` (видимость, зависимости вариантов, нормализация), `rules/findings` (метрики, правила выводов). Barrel-файлов нет (ADR-004 не менялся, уточнение Astra).

Фоновые задачи: pg-boss в той же базе; concurrency, timeout, предел повторов, idempotency key, общий бюджет соединений Prisma/pg-boss; payload содержит ссылки на данные, не данные (ADR-003).

## 3. Вход и доступ

- Команда: OIDC через Entra, допуск по членству в одной группе, сессия в HttpOnly-cookie. Ролей нет.
- Break-glass: локальный админ, выключен по умолчанию; включается флагом окружения, слушает только loopback (доступ через SSH-туннель), сессия ограничена по времени, каждое включение и вход — в AuditLog (ADR-008).
- Респонденты: ссылка с кодом RoundClient — случайный bearer ≥128 бит, с отзывом, сроком и перевыпуском. Код не попадает в логи Caddy и приложения (ADR-009). Личных токенов нет.
- Экран ведущего на семинаре: отдельный presenter-token, выпущенный заранее на семинар, чтобы день семинара не зависел от Entra (этап 3).
- Лимиты: отправки считаются по RoundClient (ожидаемая численность × запас) и глобально; per-IP лимит только как грубая защита от злоупотреблений с высоким порогом.

## 5. Приватность

Анонимность — свойство версии шаблона, не системы (ADR-025): `TemplateVersion.identification = none` (KI-опросник) или `initials` (опросник по безопасности: обязательные инициалы F1, вид по сотруднику, сравнение по людям); раунд наследует режим. Модуль `privacy` — единственная точка выдачи для дашборда, CSV, ассистента, отчётов и Atlas, с двумя классами. Класс `aggregate`, одинаковый в обоих режимах, для `part = common`: группа показывается при n ≥ 3; подавляются и дополнительные группы, восстанавливаемые вычитанием из итога; timestamps ответов хранятся с точностью до дня; прогресс наружу только суммарно; released-снимки создаются только через `privacy.release()` с подавлением по истории выдач: между любыми двумя released того же раунда Δn ячейки равно 0 или ≥ k, иначе ячейка повторяет предыдущее значение (carry-forward, `stale`); набор метрик раунда фиксируется при первом release; ручной release и ячейки прогресса идут тем же путём (ADR-021). Класс `person`, только в идентифицированных раундах: строки по человеку (`respondent_key`, роль, ответы общей части, snittscore, зона, зона предыдущего раунда по паре «клиент + инициалы») — только админ-сессия, каждое чтение в AuditLog, никогда в снимки, CSV для клиента, ассистента, Atlas и отчёт; для анонимного раунда канал отвечает 404. Часть руководителя (`part = leader`, 1–2 человека на клиента, по форме «ikkje anonymt», в обоих опросниках) никогда не соединяется с общей частью, не несёт `respondent_key` и выдаётся вне порога по отдельному правилу ADR-021: эндпоинт по одному клиенту, только админ-сессия, каждое чтение в AuditLog, не попадает в снимки, CSV, ассистент, Atlas и автоматический отчёт; правила FUNN по руководителю и кросс-правило F12×B13 идут тем же каналом (ADR-026); Oleksandr подтверждает это как обещание респондентам **[O4]**. Таблица утечек (итог + видимая роль, малые клиенты, экспорт, timestamps, `respondent_key` вне канала `person`) — в тестах и в `REVIEW-CHECKLIST.md`.

Граница доверия — по режиму раунда. **Идентифицированные раунды — вариант B, решено Oleksandr 12.10:** трое админов доверены под AuditLog, живые агрегаты с порогом в открытом раунде, канал `person`; клиент получает «samla bilete utan initialar» — агрегаты под k, выводы, сравнение с прошлым раундом, отчёт; отдельный raw-экспорт здесь не нужен. **[O3 / спор 21] Анонимные раунды (KI):** вариант A — админ-UI не доверен никому, единственный доверенный субъект — оператор базы out-of-band под журналом; дашборд показывает только released-снимки (суточные в открытом раунде), raw-экспорта нет. Вариант B — трое админов доверены под AuditLog; живые агрегаты с порогом; raw-экспорт общей части — единственное исключение из контракта для анонимной общей части (флаг + причина + AuditLog). Доверенные субъекты, каналы и отрицательные тесты — в ADR-021 и ADR-025; правило выбора по ответу Oleksandr согласовано моделями; `privacy` работает в двух режимах по `Round.identification`. Зависят только задачи [21] и [O3] в `STAGES.md`.

Хранение по классам (ADR-017, решения 12.10): ответы обоих опросников — закрытые и свободный текст, common и leader, импортированные раунды — **бессрочно**; при уходе клиента остаются; удаление только по явному запросу — по клиенту или по человеку — действием человека через `retention.forget` с записью `ForgetRequest` и AuditLog, released-снимки при этом остаются; прогресс 24 ч; released-снимки ≥ 3 года; контакты — пока есть отношение и согласие; регистрации — семинар + 90 дней; Proposal и AuditLog — 12 месяцев; `ForgetRequest` — бессрочно; backup-копии — 35 дней версионирования, поэтому удалённое по запросу исчезает из всех копий не позже чем через 35 дней, если purge корзины SharePoint подтверждён в drill 0.10, иначе — до 128 дней (ADR-016, ADR-017). Импортированные данные kartlegging: raw в Varde бессрочно; `svar.jsonl` выносится в зашифрованный архив в момент cutover (старое приложение — только redirect), архив удаляется после отчёта клиентам, но не позднее 90 дней после cutover. Остаточный риск: правовое основание хранения идентифицированных ответов после окончания договора и покрытие databehandleravtale проверяет Asbjørn **[O5]**; механизм удаления уже есть, при другом исходе меняется политика, не архитектура. Уведомление респондентам v2 (nn/en, nb по переключателю) называет инициалы и кто видит ответы по человеку, критерий хранения и удаление по запросу, факт обработки агрегатов моделью, границу доверия анонимного опросника [O3], «ответы руководителя не анонимны» [O4], роли сторон [O5].

## 6. Ассистент

Набор умений с типизированным выходом по `packages/schema`; результат всегда Proposal. Один провайдер — Azure OpenAI, один одобренный deployment в регионе ЕЭЗ (не Global), за тонким адаптером с интерфейсом «структурированный вывод, инструменты, стоимость» (ADR-010). Второй провайдер — только после подтверждённой потребности и своей проверки условий.

Что видит: агрегаты и выводы через `privacy` классом `aggregate`; выдержки из свободных ответов, подготовленные человеком и помеченные как проверенные; стилевой гайд, глоссарий, библиотеку вопросов. Никогда: инициалы, `respondent_key`, строки по человеку и строки руководителя — сборщик контекста это отклоняет (ADR-011, ADR-025). Замороженные якоря (`frozen`) умения «Редактура вопроса» и «Черновик по брифу» не трогают (ADR-005). Автоматическая обработка сырого свободного текста в v1 отсутствует (ADR-011). Инструменты только на чтение; запись только в Proposal.

Качество: автопроверки черновика (схема, выход «veit ikkje» или skip, стоп-список продуктов, ≤25 слов на вопрос без учёта текста сценария, сценарий с ответом и пояснением, все требуемые языки или пометка «к переводу»); проверка форм nn/nb; золотой набор из 10 брифов на записанных ответах в CI; живой прогон при смене любого из `(prompt_hash, deployment, briefs_version)` и перед приёмкой этапа, не ночной (ADR-018); статистика принятия. Semantic validation: цифры в тексте должны ссылаться на released-снимок. Допуск к модели — ворота G0 (checkpoint 0d с порогами из ADR-010), допуск к ассистенту в продукте — ворота G1 (одна настоящая кампания на Varde), см. `STAGES.md`.

Лимиты стоимости в день и на пользователя. Длинные задачи — через pg-boss, уведомление в админку по SSE.

## 7. Семинары (этап 3)

Seminar рождается из Findings и ссылается на раунды before/live/after. Регистрация — страница с именем, компанией, почтой, ICS; приглашение отправляет человек из своей почты (навсегда, не «пока»). Живой опрос — тот же runner в live-режиме; состояние вопросов (open → closed → released) ведёт сервер; экран ведущего получает по SSE только released-результаты и при reconnect восстанавливается из snapshot (ADR-015). Сравнение «до/после» показывает наблюдаемую динамику с оговорками (состав ответивших, самоотбор), без заявления причинного эффекта.

## 8. Живое обновление

SSE. Админка получает событие «изменилось» и перечитывает состояние через обычный API. Экран ведущего — отдельный поток с разрешёнными данными конкретного live poll.

## 9. Размещение и эксплуатация

Тот же VPS, Docker, за Caddy atlas-edge. База `varde` с ролями `varde_app` и `varde_backup` (read-only); роль Atlas не имеет доступа к `varde`, credentials независимы. Ночной `pg_dump` → шифрование (age) → rclone в SharePoint Vardahei с версионированием; restore-drill на чистой машине без исходного VPS в этапе 0 и затем ежеквартально; после восстановления повторно запускается удаление просроченных данных (ADR-016). Ёмкость VPS измеряется в этапе 0 (неделя метрик, нагрузка 100 телефонов + бэкап + AI-задача; критерий: без OOM, ≥25 % RAM в запасе, p95 отправки < 1 с, Atlas не деградирует); при провале сначала выносятся необязательные workloads.

## 10. Импорт и переключение

ImportManifest с hash источника, `source_id` только у common Response, leader Response без ключа связи, сверка по трём счётчикам (строки / common / leader), идемпотентный повтор, отчёт отклонённых. `svar.jsonl` → Response раунда 2 (для опросника по безопасности `F1` → `respondent_key`); Forms (`runde1.js`, 57 ответов по людям) → Round 1 типа `external_import` с `identification = initials` и common Response с `respondent_key` — не снимки (ADR-024, изменено 12.10): сравнение по людям и экспорт для шефа требуют строк. Метрики по F-якорям `comparable` с пояснением (ADR-020). Паритет проверяется на согласованных fixtures (синтетические инициалы) с перечнем намеренных исправлений; сверка с настоящими файлами — только числами в evidence. Production cutover — отдельная задача с чек-листом: стоп записи в kartlegging, финальный импорт и сверка, go/no-go с подписью Oleksandr, DNS, rollback до 7 дней с сохранением ответов, принятых Varde (ADR-024). Нагрузочный тест настоящего Submission API — перед cutover (ADR-016).

## 11. Тесты

`packages/rules` — табличные юнит-тесты (включая truthiness пустых значений, choices_from, exclusivity); API — интеграционные на Postgres в контейнере; runner и admin — Playwright; инварианты — обход privacy, `respondent_key` и строки по человеку вне канала `person`, канал `person` → 404 для анонимного раунда, identifier вне `answers`, replay отправки, потеря HTTP-ответа после commit, миграции, семантика ветвления; ассистент — записанные fixtures в CI, живой прогон по триггеру. Context-budget тест: ни один файл source/test/e2e/css не длиннее 700 строк.

## 12. Открытые вопросы
