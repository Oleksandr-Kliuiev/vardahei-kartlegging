# Архитектура платформы Varde

Состояние после трёх раундов brainstorm (Fable ↔ Astra) и проверки одобрения, 11.10.2026. Источник решений — `adr/`; этапы — `STAGES.md`; принципы — `PRINCIPLES.md`. Спорные места помечены **[спор N]** и ждут решения Oleksandr.

## 1. Назначение

Одна платформа для цикла «опрос → выводы → семинар → опрос после» с шестью клиентами Vardahei. Ассистент готовит черновики (опросы, переводы, объяснения, пакеты семинаров) и никогда не публикует сам. kartlegging работает до конца текущей кампании; Varde строится рядом и впитывает его данные через доказуемый импорт.

Решения Oleksandr от 11.10, не обсуждаемые: без ролей (одна группа Entra); до пяти семинаров в год, без автоотправки почты; букмол третьим языком с первого дня; без SaaS и `org_id`; условия Azure OpenAI проверяются в этапе 0.

## 2. Компоненты

```
Респонденты (телефон, ссылка с кодом)      Команда Vardahei (3, Entra)
            │                                        │
      Caddy atlas-edge (общий, TLS; query-string не логируется для runner)
            │
   Контейнер varde ──────────────────────────────────────────────
   │ apps/runner  Preact/vanilla ≤100 KB gz, nn/nb/en, draft в localStorage │
   │ apps/admin   React + Vite + TS, TanStack Query, UI на нюношке           │
   │ apps/api     NestJS + Prisma; pg-boss; модули по доменам                │
   │   privacy · surveys · rounds · metrics · findings · assistant           │
   │   seminars · imports · atlas · retention · auth                         │
   ────────────────────────────────────────────────────────────────
            │
   Postgres 17 (общий инстанс, своя база `varde`, свои роли)
            │                      │
   Atlas (API: список клиентов → ; ← observations)    Azure OpenAI (EU, один deployment)
```

Визуальный стиль — как в kartlegging (палитра, Atkinson Hyperlegible, высотный профиль с турgåar, палатка и костёр на финише), см. PRINCIPLES «Визуальный стиль».

Пакеты: `packages/schema` (zod: шаблоны, API, Proposal-выходы), `packages/rules` (движок выражений и метрик) с прямыми entry points: `rules/runner` (видимость, зависимости вариантов, нормализация), `rules/findings` (метрики, правила выводов). Barrel-файлов нет (ADR-004 не менялся, уточнение Astra).

Фоновые задачи: pg-boss в той же базе; concurrency, timeout, предел повторов, idempotency key, общий бюджет соединений Prisma/pg-boss; payload содержит ссылки на данные, не данные (ADR-003).

## 3. Вход и доступ

- Команда: OIDC через Entra, допуск по членству в одной группе, сессия в HttpOnly-cookie. Ролей нет.
- Break-glass: локальный админ, выключен по умолчанию; включается флагом окружения, слушает только loopback (доступ через SSH-туннель), сессия ограничена по времени, каждое включение и вход — в AuditLog (ADR-008).
- Респонденты: ссылка с кодом RoundClient — случайный bearer ≥128 бит, с отзывом, сроком и перевыпуском. Код не попадает в логи Caddy и приложения (ADR-009). Личных токенов нет.
- Экран ведущего на семинаре: отдельный presenter-token, выпущенный заранее на семинар, чтобы день семинара не зависел от Entra (этап 3).
- Лимиты: отправки считаются по RoundClient (ожидаемая численность × запас) и глобально; per-IP лимит только как грубая защита от злоупотреблений с высоким порогом.

Инварианты, проверяемые тестами и ограничениями БД: Response не ссылается на Contact, Registration или ProgressEvent; `submission_id` уникален; опубликованная версия не изменяется; любой выход с разбивкой проходит через `privacy`.

## 5. Приватность

Модуль `privacy` — единственная точка выдачи агрегатов для дашборда, CSV, ассистента, отчётов и Atlas. Правила для `part = common`: группа показывается при n ≥ 3; подавляются и дополнительные группы, восстанавливаемые вычитанием из итога; timestamps ответов хранятся с точностью до дня; прогресс наружу только суммарно. Часть руководителя (`part = leader`, 1–2 человека на клиента, по форме «ikkje anonymt») никогда не соединяется с общей частью и выдаётся вне порога по отдельному правилу ADR-021: эндпоинт по одному клиенту, только админ-сессия, каждое чтение в AuditLog, не попадает в снимки, CSV, ассистент, Atlas и автоматический отчёт; Oleksandr подтверждает это как обещание респондентам. Таблица утечек (итог + видимая роль, малые клиенты, экспорт, timestamps) — в тестах и в `REVIEW-CHECKLIST.md`. Released-снимки создаются только через `privacy.release()` с подавлением по истории выдач: между любыми двумя released того же раунда Δn ячейки равно 0 или ≥ k, иначе ячейка повторяет предыдущее значение (carry-forward, `stale`); набор метрик раунда фиксируется при первом release; ручной release и ячейки прогресса идут тем же путём (ADR-021).

**[спор 21]** Граница доверия: вариант A — админ-UI не доверен никому, единственный доверенный субъект — оператор базы out-of-band под журналом; дашборд показывает только released-снимки (суточные в открытом раунде), raw-экспорта нет. Вариант B — трое админов доверены под AuditLog; живые агрегаты с порогом в открытом раунде; raw-экспорт общей части (`part = common`) — единственное исключение из контракта для общей части (флаг + причина + AuditLog); часть руководителя в обоих вариантах идёт по своему правилу выше. Доверенные субъекты, разрешённые каналы и отрицательные тесты каждого варианта — в ADR-021; правило выбора по ответу Oleksandr согласовано моделями. Зависят только задачи [21] в `STAGES.md`.

Хранение по классам (ADR-017, таблица по вариантам): прогресс 24 ч; свободный текст (включая текст в части руководителя) 30 дней (A) или 90 дней (B); закрытые ответы 90 дней (A) **или** 12 месяцев (B) после закрытия раунда **[спор 17]**; released-снимки ≥ 3 года; контакты — пока есть отношение и согласие; регистрации — семинар + 90 дней; Proposal и AuditLog — 12 месяцев; backup-копии — 35 дней версионирования, поэтому удалённое исчезает из всех копий не позже чем через 35 дней, если purge корзины SharePoint подтверждён в drill 0.10; иначе — до 128 дней после удаления из основного хранилища (ADR-016, ADR-017). Импортированные данные kartlegging: raw в Varde по сроку выбранного варианта; `svar.jsonl` выносится в зашифрованный архив в момент cutover (старое приложение — только redirect), архив удаляется после отчёта, но не позднее 90 дней после cutover и не позднее срока удаления raw этого раунда в Varde. Уведомление респондентам v2 (nn/nb/en) называет точные сроки, факт обработки агрегатов моделью и границу доверия.

## 6. Ассистент

Набор умений с типизированным выходом по `packages/schema`; результат всегда Proposal. Один провайдер — Azure OpenAI, один одобренный deployment в регионе ЕЭЗ (не Global), за тонким адаптером с интерфейсом «структурированный вывод, инструменты, стоимость» (ADR-010). Второй провайдер — только после подтверждённой потребности и своей проверки условий.

Что видит: агрегаты и выводы через `privacy`; выдержки из свободных ответов, подготовленные человеком и помеченные как проверенные; стилевой гайд, глоссарий, библиотеку вопросов. Автоматическая обработка сырого свободного текста в v1 отсутствует (ADR-011). Инструменты только на чтение; запись только в Proposal.

Качество: автопроверки черновика (схема, выход «veit ikkje» или skip, стоп-список продуктов, ≤25 слов на вопрос без учёта текста сценария, сценарий с ответом и пояснением, все требуемые языки или пометка «к переводу»); проверка форм nn/nb; золотой набор из 10 брифов на записанных ответах в CI; живой прогон при смене любого из `(prompt_hash, deployment, briefs_version)` и перед приёмкой этапа, не ночной (ADR-018); статистика принятия. Semantic validation: цифры в тексте должны ссылаться на released-снимок. Допуск к модели — ворота G0 (checkpoint 0d с порогами из ADR-010), допуск к ассистенту в продукте — ворота G1 (одна настоящая кампания на Varde), см. `STAGES.md`.

Лимиты стоимости в день и на пользователя. Длинные задачи — через pg-boss, уведомление в админку по SSE.

## 7. Семинары (этап 3)

Seminar рождается из Findings и ссылается на раунды before/live/after. Регистрация — страница с именем, компанией, почтой, ICS; приглашение отправляет человек из своей почты (навсегда, не «пока»). Живой опрос — тот же runner в live-режиме; состояние вопросов (open → closed → released) ведёт сервер; экран ведущего получает по SSE только released-результаты и при reconnect восстанавливается из snapshot (ADR-015). Сравнение «до/после» показывает наблюдаемую динамику с оговорками (состав ответивших, самоотбор), без заявления причинного эффекта.

## 8. Живое обновление

SSE. Админка получает событие «изменилось» и перечитывает состояние через обычный API. Экран ведущего — отдельный поток с разрешёнными данными конкретного live poll.

## 9. Размещение и эксплуатация

Тот же VPS, Docker, за Caddy atlas-edge. База `varde` с ролями `varde_app` и `varde_backup` (read-only); роль Atlas не имеет доступа к `varde`, credentials независимы. Ночной `pg_dump` → шифрование (age) → rclone в SharePoint Vardahei с версионированием; restore-drill на чистой машине без исходного VPS в этапе 0 и затем ежеквартально; после восстановления повторно запускается удаление просроченных данных (ADR-016). Ёмкость VPS измеряется в этапе 0 (неделя метрик, нагрузка 100 телефонов + бэкап + AI-задача; критерий: без OOM, ≥25 % RAM в запасе, p95 отправки < 1 с, Atlas не деградирует); при провале сначала выносятся необязательные workloads.

## 10. Импорт и переключение

ImportManifest с hash источника, `source_id` только у common Response, leader Response без ключа связи, сверка по трём счётчикам (строки / common / leader), идемпотентный повтор, отчёт отклонённых. `svar.jsonl` → Response раунда 1; Forms (`runde1.js`) → только AggregateSnapshot раунда 0 типа external_import. Паритет проверяется на согласованных fixtures с перечнем намеренных исправлений. Production cutover — отдельная задача с чек-листом: стоп записи в kartlegging, финальный импорт и сверка, go/no-go с подписью Oleksandr, DNS, rollback до 7 дней с сохранением ответов, принятых Varde (ADR-024). Нагрузочный тест настоящего Submission API — перед cutover (ADR-016).

## 11. Тесты

`packages/rules` — табличные юнит-тесты (включая truthiness пустых значений, choices_from, exclusivity); API — интеграционные на Postgres в контейнере; runner и admin — Playwright; инварианты — обход privacy, replay отправки, потеря HTTP-ответа после commit, миграции, семантика ветвления; ассистент — записанные fixtures в CI, живой прогон по триггеру. Context-budget тест: ни один файл source/test/e2e/css не длиннее 700 строк.

## 12. Открытые вопросы

Решают не модели: спор 17 (срок raw: что нужно от данных раунда после закрытия), спор 21 (граница доверия: кто не должен восстановить отдельный ответ сотрудника), подтверждение правила для части руководителя (ADR-021), целевые RPO/RTO и заместитель (ворота G3), носитель букмола для этапа 1, доступ к OpenAPI Atlas и к администратору тенанта Entra, язык `docs/` (по умолчанию русский). Правила выбора по ответам Oleksandr согласованы моделями (ADR-017, ADR-021); архитектура и `STAGES.md` корректны при любом варианте, зависят только задачи с пометками [17] и [21].
