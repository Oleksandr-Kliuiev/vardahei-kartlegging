# Восстановление раунда из архива (5.2)

Читатели — хостинг-оператор и Oleksandr. Основание — задача 5.2 и 2.5, ADR-017/020/021; формат — `varde/apps/api/src/modules/exports/round-archive.ts`, подробности — `docs/varde/evidence/stage-5/5-evidence.md` и `docs/varde/evidence/stage-2/2a-evidence.md`.

Архив — JSON одного закрытого раунда: снимки (агрегаты), определения метрик, правила выводов семейства шаблона во всех версиях, сохранённые Finding, наборы версий правил каждого release (`finding_sets`, с 2.5) и sha256. Ответов, инициалов, `respondent_key` и кодов ссылок в нём нет. Выгрузка: «Eksport» → «Last ned arkiv» (или `GET /api/admin/exports/archive.json?round=<id>`), каждая выгрузка — запись AuditLog `exports.archive`.

Restore пишет всё в одной транзакции и ничего не перезаписывает: при отказе база остаётся как была.

## Порядок

1. **Пустая мигрированная база, до seed.** Сначала `prisma migrate deploy` на новую базу, затем restore, и только после всех restore — `seed` и остальное. Restore добавляет версию правила или метрики, только если ключа в базе нет совсем: новая версия уже известного ключа изменила бы выводы других раундов. Поэтому после первой правки в «Funn» (2.5) архив несёт версии 1 и 2, база с seed — только 1, и restore откажет весь архив. Это нормальное поведение (fail-closed), а не сбой.
2. **Несколько раундов одного семейства — от самого нового архива к старому.** В новом архиве все версии правил и метрик семейства, в старом — их подмножество. В обратном порядке второй restore упрётся в тот же отказ.
3. **Хэш выгрузки.** Без `--sha256` хэш файла защищает только от порчи: изменённый файл можно пересчитать. Хэш берётся из записи AuditLog выгрузки в исходной базе (`details.sha256`), например так же, как `SU` в `runbooks/cutover.md`:

   ```bash
   SU -d varde -Atc "select details->>'sha256' from audit_log where what = 'exports.archive' and target = 'round:<id раунда>' order by at desc limit 1"
   ```

4. **Restore** — CLI приложения в базу из `DATABASE_URL` (адрес целевой базы — через env-файл, не в командной строке; файл архива должен быть виден внутри контейнера):

   ```bash
   node dist/cli.js archive restore --file <путь к архиву> --sha256 <хэш из шага 3>
   ```

   Ответ — `{"outcome":"restored", …}` с числом снимков и Finding. Повтор того же файла — `unchanged`, ничего не меняется.
5. Проверка: дашборд и отчёт клиенту восстановленного раунда показывают те же выводы, что в исходной базе.

## Если отказ

- `sha256 does not match the content` или `not the one of the export` — файл изменён или хэш не того экспорта. Взять файл и хэш заново (место хранения и AuditLog исходной базы).
- `… in the database in other versions …` или `… is new to the … in the database …` — база не пустая или нарушен порядок. Начать заново с пустой мигрированной базы, без seed, от нового архива к старому.
- `the round exists with other content` — раунд с этим id уже есть с другим содержимым. Ничего не перезаписано; выяснить, откуда он, прежде чем что-то удалять.
- `… exists with another id` или `… has another slug/key` — в базе тот же шаблон или клиент с другим id: restore сохраняет id записей. Использовать пустую базу.
- Отказы проверки содержимого (`below k`, `does not fit`, `not an aggregate rule`, `do not follow from the archived cells`, `finding set …`, `not a round archive`) — архив не соответствует правилам выдачи или испорчен. Файл не использовать: выгрузить заново из исходной базы и сообщить Oleksandr.
